# v1.35 UC-11 訂正監査

## 1. 対象

初版完成マスター Issue #137 の `UC-11 訂正` と、詳細仕様書 v2.5 第14章 `COR-001〜010 訂正・返品・取消` を現行 `develop/v1.35` に突合する。

UC-11 は独立した「CORRECTION」確定取引種別を新設する要件ではない。仕様書の訂正契約は次の二層で構成される。

- **未確定取引の訂正**: COR-001 置数訂正 / COR-002 直前訂正 / COR-003 任意行訂正 / COR-004 取引中止
- **確定済み売上の訂正**: COR-005〜010 の返品・取消・返金・日計後訂正・削除禁止を使用し、元取引を直接書き換えず反対取引として追記する

このため、既存 COR 実装を再利用し、重複する確定訂正台帳や別の返金ロジックは追加しない。

## 2. 仕様突合

### COR-001 置数訂正

- `NumericCorrectionPolicyV135`
- 販売画面の `C` / `訂正`
- 置数が残っている間は明細を変更せず置数だけを消去する。

### COR-002 直前訂正 / COR-003 任意行訂正

- `CartCorrectionV135`
- `RegisterDatabase.applyCartCorrection`
- `cart_correction_history`
- `CartItem.lineId`

直前行または選択行を取消し、元行識別子・取消数量・取消額・担当者・時刻を作業中履歴へ追記する。全量取消は有効行を除去し、一部取消は残数量へ更新する。取消履歴は有効明細と分離し、税・小計・会計・売上集計へ混入しない。

### COR-004 取引中止

- `TransactionAbortV135`
- `operation_audit`

未確定カートだけを破棄し、理由・担当者・営業日・明細数・数量・金額を監査ログへ保存する。確定 `sales` は生成・更新しない。

### COR-005 / COR-006 返品

- `PartialReturn.kt`
- `OperationsStore.createReversal`
- `ManualReturnV135`

元取引あり返品は `reversal_transactions / reversal_items / reversal_payments` へ追記し、残数量を超える返品を拒否する。元取引なし返品は専用追記台帳を使用する。

### COR-007 売上取消

- `OperationsStore.createReversal`
- `SaleReversalTraceV135`
- `BusinessDateSalesLookupActivity`

取消は全量反対取引として追記し、`original_sale_id` で元売上を保持する。元売上は `取消済（VOIDED）` 相当表示となり、反対取引を参照できる。元売上そのものは更新・削除しない。

### COR-008 支払返金

- `PartialReturnPolicy.allocateRefundPayments`
- `ManualRefundFallbackV135`
- `SecureOperationsCoordinator`

元支払内訳と既返金額から返金可能残高を計算し、元支払種別へ返金する。自動復元できない場合だけ責任者承認後の手動返金方法選択へフォールバックする。

### COR-009 日計後訂正

`OperationsStore.createReversal` は訂正実行時の OPEN 営業セッションを取得し、反対取引へ以下を保存する。

- `business_session_id = session.id`
- `business_date = session.businessDate`
- `original_sale_id = originalSaleId`

したがって、過去営業日または既に Z 精算済みの売上を後日訂正しても、減額は訂正実行日の営業日に計上される。元営業日の `sales` と過去 `settlement_reports` は書き換えない。

### COR-010 削除禁止

確定売上・返品・取消・入出金は追記方式とし、通常アプリコードから確定業務テーブルを物理 DELETE しない累積ソースゲートを維持する。

## 3. UC-11重点安全条件

### 元取引を直接書き換えない

確定済み売上の訂正は `reversal_transactions` へ追記する。`sales / sale_items / sale_payments / settlement_reports` の UPDATE / DELETE は訂正処理から行わない。

### 支払返金

返金額は元支払残高から既返金額を控除した容量内だけ配賦する。現金・カード等の複合支払も一重に返金集計へ反映する。

### 返品・取消との二重適用防止

- 一部返品済み売上の全量取消を拒否する。
- 全量返品 / 取消済み売上は売上照会・返品取消画面で再選択不可とする。
- 返金済数量は元数量を超えない。

### 冪等性

`operation_commit_keys` を永続重複防止に使用する。

- CANCEL: `CANCEL:<originalSaleId>` 固定。requestIdを変えても再取消不可。
- RETURN: `RETURN:<originalSaleId>:<requestId>`。同一要求の再送は重複確定不可。

### 監査・印刷・同期

確定後訂正は反対取引保存と同一DBトランザクションで監査ログと保存済み印刷payloadを作成する。成功後に印刷スケジューラと Drive Outbox を起動する。X点検 / Z精算は反対取引・返金支払を営業セッション単位で一重集計する。

## 4. UC-11専用自動ゲート

`V135Uc11CorrectionAuditTest` で以下を累積固定する。

1. COR-001〜004 の既存作業中訂正実装を単一実装として使用する。
2. 確定済み訂正は `original_sale_id` を持つ追記反対取引であり、元売上・元支払・旧精算を直接更新 / 削除しない。
3. 支払返金が元支払残高・既返金残高へ拘束される。
4. 一部返品後の取消を拒否し、返品 / 取消の二重適用を防ぐ。
5. RETURNの同一request再送と、CANCELのrequestId変更による再実行を永続冪等性キーで防止する。
6. 監査ログ、返品・取消票、印刷スケジューラ、Drive Outboxが既存訂正処理から維持される。
7. 過去 `settlement_reports` を訂正処理から書き換えない。

既存の COR-001〜010 専用テストと合わせて累積CIで実行する。

## 5. 実機確認として残す項目

自動確認済みと実機確認済みを混同しない。以下は **未確認** とする。

1. 置数入力後の `C` / `訂正` で置数だけが消える。
2. 直前訂正で直前行が取消履歴へ残り、表示合計が即時更新される。
3. 任意行の全量 / 一部訂正、値引済み複数量行の一部訂正。
4. 取引中止の理由必須、担当者監査、売上非計上。
5. 過去 Z 精算済み売上を翌営業日に返品 / 取消し、翌営業日の集計だけが減額され、旧 Z が不変である。
6. 現金返金と現金理論残高。
7. 複合支払の返金内訳。
8. 一部返品後の取消拒否、全量処理後の再返品 / 再取消拒否。
9. 確定連打、同一要求再送、アプリ再起動後の永続二重適用防止。
10. 58mm / 80mm の返品・取消票、元売上No.・負数量・負金額・返金情報。
11. 売上照会の `一部返品 / 返品済 / 取消済（VOIDED）` と反対取引参照。
12. X点検 / Z精算への純売上・支払別・現金理論残高の実機反映。
13. カード等の外部決済端末側の実返金 / 実取消との一致。外部決済端末本体の実連携は v1.38 対象。

## 6. 判定

UC-11 は、独自の重複実装を追加するのではなく、既存 COR-001〜010 を一つの訂正業務契約として固定する。コード・自動テスト・CI・APK独立検証を通過後も、上記実機項目が残るため Issue #137 上の「実機確認済み」にはしない。
