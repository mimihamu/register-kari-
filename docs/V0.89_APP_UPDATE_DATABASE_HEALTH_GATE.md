# v0.89 上書き更新成功前 DB健全性ゲート

## 目的

v0.88では、APK上書き更新後に `MainActivity` が `RESUMED` へ到達した時点を通常画面まで起動できた証拠として、更新成功版を永続記録する仕組みを追加した。

ただし、画面が表示できることとSQLiteの健全性は同義ではない。SQLiteファイル破損、外部キー不整合、必須テーブル・必須列欠落が残っていても、参照されていない箇所なら `MainActivity` が表示できる可能性がある。その状態を `APP_UPDATE_STARTUP_SUCCEEDED` と記録すると、現場で「更新成功」と誤認する恐れがある。

v0.89では、**MainActivity RESUMED後・更新成功確定前**に現在DBを読み取り専用で検査し、DB健全性が確認できた場合だけ成功版を確定する。

## Provider順序

同一プロセスのProviderは以下を維持する。

1. `DataRestoreBootstrapProviderV086` / `initOrder=1000`
2. `AppUpdateTransitionBootstrapProviderV089` / `initOrder=900`
3. 通常Provider群 / `initOrder=150`以下

v0.89 Providerはv0.88 ProviderをManifest上で置き換える。v0.88のクラスはソース互換用として残すが登録しない。

更新台帳SharedPreferences名と主要キーはv0.88と同じ値を使用し、v0.88までの正常版・未完了証跡をそのまま引き継ぐ。

## DB健全性確認

`AppUpdateDatabaseHealthCheckV089` は `register.db` を `SQLiteDatabase.OPEN_READONLY` で開き、以下を確認する。

- `PRAGMA user_version`
- `PRAGMA integrity_check` が単一 `ok`
- `PRAGMA foreign_key_check` が0件
- 主要必須テーブルの存在
- 後付けスキーマ主要列の存在

必須テーブルはデータ保全対象の基本テーブルに加えて以下を確認する。

- `document_print_jobs`
- `operation_commit_keys`
- `receipt_voucher_batches`
- `receipt_voucher_issuances`
- `receipt_voucher_reprints`
- `sale_receipt_reprint_requests`

主要列はv0.85起動時スキーマ確認と同等の以下を確認する。

- `cart_items`: `line_no`, `discount_amount`, `note`
- `sales`: `print_count`, `business_session_id`, `business_date`
- `sale_items`: `discount_amount`, `note`
- `held_ticket_items`: `discount_amount`, `note`
- `reversal_items`: 税スナップショット関連列
- `settlement_reports`: `opening_cash`, `cash_in`, `cash_out`, `snapshot_version`

## 健全性NG時

1. 更新成功版を確定しない。
2. v0.88互換のpending更新証跡を残す。
3. `app_update_database_health_v089` SharedPreferencesへ、対象版・確認時刻・サニタイズ済み概要を同期保存する。
4. 不健全なSQLiteへ `operation_audit` を書かない。
5. 販売画面をこの診断機能だけを理由にクラッシュさせない。
6. 次回起動で再度DB健全性を確認する。

SQLite例外の生メッセージやDB絶対パスは失敗証跡へ保存せず、例外クラス名だけを保持する。

## 健全性OK時

DB健全性を確認した後だけ既存の更新監査へ進む。

- `APP_VERSION_BASELINE_ESTABLISHED`
- `APP_UPDATE_STARTUP_SUCCEEDED`
- `APP_UPDATE_STARTUP_RECOVERED`
- `APP_UPDATE_PREVIOUS_STARTUP_INCOMPLETE`

同一target版で以前DB健全性NGが記録されており、今回OKへ回復した場合は以下も追記する。

- `APP_UPDATE_STARTUP_DB_HEALTH_RECOVERED`

成功監査detailにはDB health、`user_version`、integrity、FK件数を含める。

## データ保護

v0.89健全性チェック自身は以下を行わない。

- `writableDatabase` の取得
- `execSQL`
- `INSERT` / `UPDATE` / `DELETE`
- `ALTER TABLE` / `DROP TABLE`
- sales / sale_items / sale_payments / products / held tickets の変更
- Sales Journal / Drive JSON / sync fingerprint / SENT Outbox / 隔離・同期履歴の削除
- ロールバックDBの削除

DBが健全と判定された後に限り、従来どおり追記専用 `operation_audit` へ更新成功監査を追加する。

## 実機確認項目

- v0.88→v0.89上書き更新でv0.88のlast-successをsourceとして引き継ぐこと
- 正常DBでMainActivity RESUMED後に更新成功監査が残ること
- DB破損時に成功版が確定されないこと
- 外部キー不整合時に成功版が確定されないこと
- 必須テーブル／列欠落時に成功版が確定されないこと
- DB健全性NG時に業務DBへ監査書込みしないこと
- NG後に正常バックアップ復元等で健全化した際の回復監査
- WAL有効・営業データ量大の端末でintegrity check中もUIが固まらないこと
- 端末強制終了／再起動後もpendingとDB-health failure evidenceが保持されること

これらはCI・JVM unit testだけでは実Android SQLite動作確認済みとは扱わない。
