# v1.92 BKP-REST 支払証跡が残るDBの復元上書きを防止

## 背景と問題
BKP-004の復元予約では営業中・通常カート・印刷キューなどを拒否していたが、カートが空になったあとにも残る `payment_external_pending_v188`（端末結果不明）や `payment_draft_allocations`（未確定/未整理の支払）を直接チェックしていなかった。復元は既存register.dbを別DBに置き換えるため、未解決の決済証跡を失わせて二重決済の調査を困難にし得た。

## 変更
- `RestoreFinancialEvidenceV192.requireSafeToReplace()` は現存DBを読み取り専用で開き、上記2テーブルのレコード件数を取得。1件でも存在すれば復元を拒否。テーブル欠損は旧バージョンDB互換として0件。SQL読み取りエラーは例外伝播して復元拒否。
- `RestoreReservationCoordinatorV116.stage()` は書込みフェンスを設置する前に拒否。
- `DataProtectionManager.stageRestore()` も直接呼出に備えてガードを実行。
- `PendingRestoreApplierV086.applyIfPresent()` は次回起動時、ロールバックコピー/元DB側car削除/DB置換の前に再検査。予約後の異常状態でも元DBを温存し、失敗履歴を記録。
- 復元候補DBに未解決決済がある場合は、候補DB内の記録を破棄せず通常の支払復旧画面へ引き継ぐ設計。今回のガードは**現在端末のDB上書き**を防止する。
- 追加テスト `V192RestoreFinancialEvidenceFenceTest` はブロック判定、両予約経路、起動時二重ガード、読み取り専用アクセスを検証。

## 制限
実機でのバックアップ復元リハーサル・SQLite破損注入・カード端末の履歴照合・販促や周辺機器の動作確認は未受入。本番公開や正式署名は行わない。
