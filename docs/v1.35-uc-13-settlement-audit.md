# v1.35 UC-13「精算」監査

対象: 仕様書 v2.5 `UC-13` / `REP-002`〜`REP-005`（関連: `BIZDAY-001`）

## 判定

ローカル機能はコード実装・自動テスト・APK検証対象まで進める。**実機未確認のため初版完成チェックリスト上は完了扱いにしない。**

## 仕様突合

### REP-002 日計精算

- OPEN営業セッションだけをZ精算対象にする。
- 同一営業セッションのZ二重実行を拒否する。
- 永続operation keyで再送・再タップの重複登録を防ぐ。
- Z確定時は営業セッションを条件付きで `OPEN -> Z_SETTLED` 相当に遷移する。
- 売上・返品・取消・支払等の元明細は削除しない。

### REP-003 精算前確認

Z実行前に以下を評価する。

- 未会計伝票
- 未印刷ジョブ
- 作業中カート
- 未完了決済
- 直近バックアップ失敗
- 現金実査未入力

継続可能な警告は明示確認を要求し、確認した事実を監査ログへ残す。現金実査はZで必須。

### REP-004 精算スナップショット

従来は `settlement_reports`、`settlement_payment_totals`、`settlement_rep001_totals_v135` が主要値を固定していた一方、税率別は元取引スナップショットから再集計し、店舗名・住所・電話・登録番号は再表示時の現在設定を参照していた。また仕様が要求するJSONスナップショットが存在しなかった。

v1.35ではスナップショット版を `2` とし、Z/X保存と同じSQLiteトランザクション内で以下を追加保存する。

- `settlement_snapshot_metrics_v135`
  - 値引、税額互換値、点数、客数
  - 現金実査入力有無
  - 店舗名、住所、電話、適格請求書登録番号
- `settlement_snapshot_tax_v135`
  - 税率、課税/非課税、対象額、税額
- `settlement_snapshot_json_v135`
  - ヘッダ、営業日/営業セッション、担当者
  - 売上/返品取消/純売上、件数、客数、点数、値引
  - 開始釣銭、入出金、理論/実査/過不足
  - 未印刷/未会計件数
  - 支払別
  - 税率別
  - 店舗・登録番号

既存の正規化テーブル `settlement_reports` と `settlement_payment_totals` はそのまま利用する。

再表示・再印字・PDF保存は、新しいsnapshot v2が存在する場合は固定済みの店舗情報、REP-001集計、税率別、現金実査入力状態を優先する。旧snapshot v0/v1は従来の確定時刻cutoff/保存済み初回印字payloadによる互換経路を維持する。

### REP-005 精算取消禁止

通常の精算実行・履歴・再印字経路に `settlement_reports` の物理削除やZのOPEN巻き戻しを設けない。誤精算を履歴から消す設計にはしないため、Z番号・監査履歴の連続性を保持する。

## 自動検証

`V135Uc13SettlementAuditTest` で以下を累積ゲート化する。

1. snapshot v2 + JSON + 正規化metrics/taxテーブルの存在
2. `settlement_payment_totals` 保存経路から同じDBトランザクションでREP-004保存を呼ぶこと
3. 再表示/再印字/PDFが固定済み税率別・店舗情報・実査入力状態を優先すること
4. Z二重精算防止、永続operation key、OPEN営業セッションの条件付きclose
5. REP-003の警告/阻止条件
6. 通常精算経路にsettlement削除/OPEN巻き戻しがないこと

加えて既存の累積テスト、Kotlin compile、3 APK buildを通す。
