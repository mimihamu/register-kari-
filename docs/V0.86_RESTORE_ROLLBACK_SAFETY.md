# v0.86 復元ロールバック安全化

## 1. 背景

v0.83では、起動時の復元処理を他のDB利用Bootstrapより先に実行するようにし、復元前の現在DBを `data_restore/rollback-register-<timestamp>.db` として残す仕組みを導入していた。

しかし、v0.85までの復元処理には次の運用リスクが残っていた。

1. 現在DBをそのまま `File.copyTo()` してから `register.db-wal` / `register.db-shm` を削除していた。
2. SQLiteがWALモードで、確定済み取引がWAL側に残っている場合、コピーした `register.db` 単体には最新の確定データが入っていない可能性がある。
3. ロールバックコピー作成中に容量不足・I/Oエラーが発生した場合も、本DB置換後の失敗と同じcatchへ入り、元DBを削除してから不完全なロールバックを戻そうとする経路があった。

「ロールバックファイルが存在する」だけではデータ保護として不十分であり、**ロールバックファイル自体が最新かつ一貫したSQLite DBであることを本DB置換前に確定する必要がある**。

## 2. v0.86の方針

起動時復元Providerを `DataRestoreBootstrapProviderV086` へ切り替える。

旧 `DataRestoreBootstrapProvider` はコードとして残すが、AndroidManifestから登録を外し、通常起動時には実行されない。

initOrderはv0.83で確定した `1000` を維持する。

これにより、復元処理は引き続きCatalog / Outbox / Drive / 印刷 / CD等より先に実行する。

## 3. 復元前ロールバックの確定手順

現在DBが存在する場合、次の順で `RestoreRollbackSafetyV086.createVerifiedSnapshot()` を実行する。

1. `register.db` を `SQLiteDatabase.OPEN_READWRITE` で開く。
2. `PRAGMA wal_checkpoint(FULL)` を実行する。
3. checkpoint結果の `busy == 0` を確認する。
4. WAL総frame数とcheckpoint済frame数が一致することを確認する。
5. 現在DBに `PRAGMA integrity_check` を実行する。
6. 現在DBに `PRAGMA foreign_key_check` を実行する。
7. `rollback-register-<timestamp>.db.tmp` へコピーする。
8. 一時ロールバックDBに再度SQLite整合性・外部キー検査を実行する。
9. 一時ロールバックDBのSHA-256を算出する。
10. 検証成功後のみ正式な `rollback-register-<timestamp>.db` へatomic replaceする。
11. 正式ロールバックDBを再度検証し、SHA-256が一時コピーと一致することを確認する。

**ここまで完了する前は、現在の `register.db` / `register.db-wal` / `register.db-shm` を削除しない。**

## 4. ロールバック作成に失敗した場合

容量不足、checkpoint未完了、SQLite整合性エラー、コピー失敗、SHA不一致等で安全なロールバックを確定できなかった場合は、復元自体を中止する。

この経路では以下を行わない。

- 現在DBの削除
- 現在DBの置換
- 現在DBのWAL削除
- 現在DBのSHM削除

復元予約の `restore-plan.properties` と `pending-register.db` は破棄し、`restore-result.txt` に「復元中止・元DB保持」を記録する。

元の `.tgbak` バックアップアーカイブは `data_backups` に残るため、原因解消後に責任者が改めて復元予約できる。

## 5. 本DB置換後に復元が失敗した場合

安全なロールバック確定後のみ、以下を行う。

1. 現在DBのWAL/SHMを削除する。
2. `pending-register.db` を `register.db` へatomic replaceする。
3. 復元DBのSQLite整合性を検証する。
4. 必須テーブルを検証する。
5. `DATA_RESTORE_APPLIED` 監査を追記する。

この途中で失敗した場合は、作成済みの検証済みロールバックDBから元DBを復旧する。

復旧時も直接上書きせず、次の順で行う。

1. 保持中ロールバックDBを再検証する。
2. `register.db.rollback-restore.tmp` へコピーする。
3. 一時復旧DBをSQLite整合性・外部キー・SHAで検証する。
4. 旧WAL/SHMを削除する。
5. 一時復旧DBを `register.db` へatomic replaceする。
6. 復旧後の `register.db` を再検証する。
7. 作成時SHA-256と一致することを確認する。

ロールバック元の `rollback-register-*.db` 自体は削除しない。

## 6. 復元成功記録

復元成功時の `restore-result.txt` には以下を残す。

- 復元元バックアップ名
- 復元日時
- 復元前ロールバックDB名
- 復元前ロールバックDBのSHA-256

`DataProtectionActivity` では従来どおり `restore-result.txt` の最終結果を表示するため、責任者は復元後にロールバックファイル名とSHAを確認できる。

## 7. 自動削除しないデータ

v0.86で以下の自動削除・上書き仕様は追加しない。

- 売上 `sales`
- 売上明細 `sale_items`
- 支払明細 `sale_payments`
- 保留伝票
- 商品マスター
- Sales Journal
- Drive JSON
- sync fingerprint
- SENT Outbox
- 隔離データ
- 同期履歴
- 復元前ロールバックDB

本DBの置換は、責任者が事前に予約した正式な復元処理の実行時だけ行う。

## 8. v0.83 / v0.84 / v0.85との関係

- v0.83: 復元Providerを他Bootstrapより先に実行
- v0.84: SQLiteOpenHelperの破壊的DROP移行を廃止
- v0.85: DB user_versionに依存せず後付けスキーマを起動前整備
- v0.86: 復元前ロールバックをWAL-safe・検証済みにし、復元失敗時の元DB復旧経路を安全化

v0.86は上記を置き換えるのではなく、累積して適用する。

## 9. 実機で確認が必要な項目

コード・CIだけでは次を確認済みとはしない。

1. WALに未checkpointの確定取引がある状態で復元予約→再起動
2. ロールバックDBに直前売上が含まれること
3. WAL checkpoint結果が端末SQLiteで想定どおり取得できること
4. 容量不足でロールバック一時コピーに失敗した場合、元DBが保持されること
5. 復元DBを意図的に異常化した場合、元DBへ戻ること
6. 復元後の販売・保留・売上履歴・精算・領収書・再印字
7. 端末再起動・強制終了を復元前後に挟んだ場合
8. 大容量DBでの起動時間とロールバック作成時間

実機未確認事項は、確認完了まで「確認済み」と扱わない。
