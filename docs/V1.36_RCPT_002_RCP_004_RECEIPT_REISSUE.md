# v1.36 RCPT-002 / formal v2.5 RCP-004 後レシート・再発行表記

## 仕様突合
Issue #137 #25 の `RCPT-002 再発行表記` は、正式仕様書 v2.5 の RCP-004「後レシート」および §16.4 販売レシート印字順序を実装基準とする。

正式仕様の要点:
- 直前取引または売上一覧から後レシートを発行できる。
- 再発行レシートは最上端と末尾の両方へ「再発行」を必須表示する。
- 通常売上では再発行表示を出さない。
- 再発行回数、担当者、日時を監査記録する。
- 後レシートは自動レシート発行OFFでも利用可能。
- プリンター送信失敗ジョブの単なる再試行は新しい再発行操作として数えない。

## 実装
- `ReceiptRenderer` は `reprint=true` の場合、任意ヘッダや店舗情報より前の最上端に `【再発行】` を印字する。
- 任意フッタの後、レシート最終行にも `【再発行】` を印字する。
- 58mm / 80mmで同一ルールを使用する。
- `RegisterDatabase.enqueueReprint(saleId, actor)` は後レシート用印刷ジョブと監査レコードを同一SQLite transactionで登録する。
- 監査イベントは `SALE_RECEIPT_REPRINT_ENQUEUED`。同一売上の過去イベント件数から `再発行回数=N` を記録し、担当者、登録日時、print job ID、紙幅も保存する。
- `OperationAuditSchemaV136.ensure()` により、AdvancedOperations画面を一度も開いていない端末でも後レシート監査テーブルを冪等に作成できる。
- 売上一覧/レシートプレビューからの操作は現在ログイン中の `operatorName` を監査担当者として渡す。
- `retryPrintJob()` は既存ジョブの送信再試行であり、`SALE_RECEIPT_REPRINT_ENQUEUED` を増やさない。

## 自動テスト
`V136ReceiptReissueMarkTest.kt` で以下を固定する。
- 58mm / 80mmとも再発行マークが先頭・末尾のちょうど2箇所。
- 任意ヘッダより再発行マークが先に来る。
- 通常レシートには再発行マークがない。
- 後レシート登録経路が担当者付き監査を作り、retry経路では再発行回数を増やさないsource contract。

## 実機確認
58mm / 80mm実プリンターでの上下「再発行」視認、紙切れ復旧後の再試行、後レシート複数回時の監査履歴照合は最終統合受入で実施する。実機確認済みとは扱わない。
