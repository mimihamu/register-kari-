# v1.29 Drive verification history atomic publication

## 背景

v1.26でDrive API failure historyをfinalized direct statusと一致させ、v1.27でWorkManager由来の成功・失敗も同じ同期検証履歴へ保存するようにした。

これにより、手動ダッシュボード同期、WorkManager同期、隔離データ個別再試行が同一の`GoogleDriveSyncVerificationHistoryStore`へ履歴を追加する。

## 問題

v1.28までの`append()`は次のread-modify-writeだった。

1. `load()`で現在履歴を読む
2. 新recordを先頭へ追加して最大20件へ切る
3. JSONへ変換
4. SharedPreferencesへ`apply()`する

この複合処理全体に排他がなかったため、例えば手動同期とWorkManagerがほぼ同時に完了すると、両者が同じ旧履歴を読んだ後にそれぞれ別内容を書き戻せる。

その場合、最後に書いた側だけが残り、先に完了した同期の監査recordが履歴から消えるlost updateが発生し得る。

`clear()`と`append()`の近接実行も同じread/write境界を共有していなかった。

## v1.29の修正

`GoogleDriveVerificationHistoryMutationGateV129`を追加し、アプリprocess内で共有する公平な`ReentrantLock`を持たせる。

`GoogleDriveSyncVerificationHistoryStore`は次を同じexclusive gateへ通す。

- `load()`
- `append()`のread-modify-write全体
- `clear()`

`append()`はexclusive区間の中で`loadUnlocked()`を実行し、新record追加・20件制限・JSON生成・SharedPreferences更新までを完了する。

これにより、同一process内の複数Store instance、Activity、WorkManagerからのhistory mutationは直列化される。

SharedPreferencesの`apply()`は呼出し時にprocess内のin-memory値を更新するため、gate解放後の次mutationは直前にpublishした履歴を基準にできる。ディスク書込みをUI threadで同期化する`commit()`への変更は行わない。

- v1.22 Drive import + fingerprint atomic commit
- v1.23 page commit後のpartial progress保持 / 新run counter reset

## 変更しないもの

- SQLite / Management DB schema
- Drive fingerprint schema
- direct status SharedPreferences schema
- verification history JSON field形式
- WorkManager unique work / periodic schedule / coalescing policy
- Drive repository single-flight
- Compatibility Folder同期内容

## process境界

v1.29のmutation gateは同一Android application process内の競合を防ぐ。

現在のつぐレジ＋はこの履歴を複数processから更新する構成ではない。将来android:process等で別process writerを追加する場合は、SharedPreferences read-modify-writeではなくDB transaction等のcross-process永続化境界を別途設計する。

## テスト

`V129DriveVerificationHistoryMutationGateTest`で、複数threadが同時にgateへ入ろうとしてもcritical section内の最大同時実行数が1であること、および戻り値を保持することを確認する。

CI source gateでは、HistoryStoreの`load`/`append`/`clear`が同じV129 gateを使用し、`append`が`loadUnlocked()`をexclusive区間内で利用する構造を確認する。

## 実機未確認・最終総合実機試験へ繰越し

- 手動Drive同期とWorkManager同期を近接完了させた場合に両recordが履歴へ残ること
- WorkManager retryと手動同期が近接した場合に履歴recordが欠落しないこと
- 隔離データ個別再試行とバックグラウンド同期の近接完了
- 履歴消去とバックグラウンドappendが近接した場合の最終表示
- アプリ再起動後の履歴永続化

CI成功のみでこれらを実機確認済みとは扱わない。
