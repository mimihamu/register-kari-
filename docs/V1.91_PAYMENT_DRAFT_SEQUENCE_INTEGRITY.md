# v1.91 支払下書きの明細番号を非破壊で検証

## 発見した不具合
`payment_draft_allocations.sequence_no` に欠番（例: 1,3）が発生しても、従来の`load()`は明細の金額・支払方法だけ復元できた。続く`save()`や`cancelAllocation()`で`forEachIndexed`を使って1,2と連番を付け直すため、**異常の証拠を黙って上書き**する経路があった。

## 修正
- `PaymentDraftSequenceV191.requireContiguous()`を追加。SQLite上の`sequence_no`を`getLong()`で読み、1始まり・欠番なし・重複なしを検査。
- `PaymentDraftStore.save()`（既存支払がある場合）/ `cancelAllocation()` / `beginExternalTender()` / `resolveExternalTender()` は下書き番号を変える前に検査。異常があればトランザクションをロールバック。
- `load()`では支払復旧の前に検査し、異常時は自動復元を拒否。下書き・保留決済の証拠を保存する。
- `clear()`では確定売上との照合が成立しても、元の明細番号が壊れていれば自動消去しない。
- `V191PaymentDraftSequenceIntegrityTest`を追加。連番、欠番、重複、0/負値、32bit超過、各経路の未検証再書込防止を検証。

実機での強制終了、実決済端末の履歴照合、印刷・CD通信、正式署名/OTA本番公開は未受入。
