# v1.30 Drive verification history crash recovery

## 背景

v1.26ではDrive API failure historyをfinalized direct statusと一致させ、v1.27ではWorkManager同期も同じ検証履歴へ保存するようにした。v1.28ではforeign runの件数誤帰属を防ぎ、v1.29では複数writerによるhistory lost updateをprocess-wide mutation gateで防止した。

一方、direct statusとverification historyは別SharedPreferencesへ保存される。

Drive repositoryは同期結果を先に`GoogleDriveDirectSyncStatusStore.complete()`または`failedForRun()`でfinalizeし、その後Activity/Workerが`GoogleDriveSyncVerificationHistoryStore.append()`を呼ぶ。

## 問題

次の狭いcrash windowが残っていた。

1. 売上JSONの取込・fingerprint commitが完了する
2. direct statusが`running=false`、`lastCompletedAt`、件数、failure categoryを含むfinalized状態になる
3. verification historyへrecordをappendする前にprocessが終了する

この場合、業務データとdirect statusは確定済みだが、監査履歴だけが欠落する。

次回WorkManager runが開始するとdirect statusが新runで上書きされるため、起動時に補完しないと欠落した最終runの監査情報を後から復元できなくなる。

## v1.30の修正

`GoogleDriveVerificationHistoryRecoveryProviderV130`をつぐレジ＋へ追加する。

- `android:initOrder=200`
- 既存`GoogleDriveDirectSyncBootstrapProvider`は`initOrder=100`
- recovery providerを先に起動し、bootstrapがWorkManagerをscheduleする前に監査整合性を確認する
- networkアクセスやDB更新は行わず、direct statusとverification historyのSharedPreferencesだけを使用する

### 新しいfinalizationだけを対象にする

単純に「最新direct statusに対応するhistoryが無いなら補完」すると、ユーザーが明示的に履歴消去した後の再起動で履歴を復活させてしまう。

そのため`GoogleDriveVerificationHistoryRecoveryStateStoreV130`で`observed_completed_at`を保持する。

初回v1.30起動時は現在の`lastCompletedAt`をbaselineとして記録し、過去versionの履歴を勝手に再生成しない。

その後は、次の条件をすべて満たす場合だけ新finalizationとして確認する。

- direct statusが`running=false`
- `lastCompletedAt`が存在する
- `lastCompletedAt > observed_completed_at`

historyに同じfinalized statusを表すDrive API recordが既にあれば追加せず、watermarkだけ進める。

一致recordが無い場合のみ、finalized direct statusから復旧recordを1件appendする。

### 履歴消去を尊重する

recovery providerはprocess lifetime中、verification history SharedPreferencesの`history`変更listenerを保持する。

通常のappendまたは明示的なhistory clearが発生すると、その時点のfinalized `lastCompletedAt`をobserved watermarkへ反映する。

これにより、明示的に消去した最新履歴は再起動時に復活しない。

### 重複復旧防止

復旧前にhistoryを確認し、次が一致するDrive API recordが`lastCompletedAt`以後に既に存在する場合は補完しない。

- mode
- success semantics
- listed
- imported
- duplicate
- rejected
- normalized error count

failure statusでは既存v1.26 semanticsと同様にhistory `errorCount`を最低1とする。

復旧record自身は`recordedAt=lastCompletedAt`とするため、復旧append後にprocessが再度終了しても次回起動で同一finalizationを重複生成しない。

## 維持する保証

- v1.21 Drive sync single-flight / run-token ownership / immediate work coalescing
- v1.22 Drive import + fingerprint atomic commit
- v1.23 page commit後のpartial progress保持 / 新run counter reset
- v1.24 importer compatibility signature / transport fingerprint reset境界
- v1.25 failure progress ownership
- v1.26 finalized failure statusとhistory件数一致
- v1.27 WorkManager verification history
- v1.28 foreign/newer direct statusのfailure history誤帰属防止
- v1.29 verification history mutation serialization / lost-update防止
- history最大20件
- 既存history JSON schema

## 変更しないもの

- SQLite / Management DB schema
- Drive fingerprint schema
- direct status SharedPreferences schema
- verification history JSON field形式
- Drive repositoryのcommit順序
- WorkManager unique work名、周期、coalescing policy
- Compatibility Folderの同期・history semantics

v1.30で追加するのはrecovery専用watermark SharedPreferencesのみで、業務データschemaは変更しない。

## 対象外

`running=true`のままprocessが落ちたケースはfinalized結果ではないため、v1.30はhistoryを合成しない。既存のstale-run recovery境界を維持する。

初回v1.30起動時も既存statusをbaseline化し、過去versionで欠落していた可能性があるhistoryを推測復旧しない。

## テスト

`V130DriveVerificationHistoryRecoveryTest`で以下を確認する。

- finalized successに対応するhistoryが無ければ復旧recordを生成
- 同じfinalized statusのhistoryが既にあれば重複生成しない
- running statusはfinalized historyとして合成しない
- finalized failureのhistory errorCountを最低1へ正規化
- 同件数の古いhistoryで新しいmissing finalizationを隠さない
- observed watermarkと同一または古いfinalizationは再処理しない
- observed watermarkより新しいfinalizationだけを復旧候補にする

CI source gateでは、recovery providerのinitOrderがbootstrapより高いこと、listenerがhistory変更時にwatermarkを更新すること、reconcileが新finalizationだけを対象にすることを確認する。

## 実機未確認・最終総合実機試験へ繰越し

- direct status finalize直後、history append前にprocess killした場合の次回起動補完
- 成功run / partial failure / preflight failureそれぞれの補完表示
- history append済みrunで再起動しても重複recordが増えないこと
- 履歴消去後に再起動しても消去した最新recordが復活しないこと
- recovery providerがWorkManager bootstrapより先に実端末で動作すること
- `running=true` crash後の既存stale-run recoveryとの組合せ

CI成功のみでこれらを実機確認済みとは扱わない。
