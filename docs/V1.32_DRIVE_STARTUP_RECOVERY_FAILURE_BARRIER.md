# v1.32 Drive startup recovery failure barrier

## 背景

v1.30ではfinalized direct statusからverification historyを復旧し、v1.31ではAndroid process終了後に残った`running=true`のDrive runをWorkManager bootstrapより先に中断確定するようにした。

v1.31ではorphaned runのstatusを`SharedPreferences.Editor.commit()`でdurableに確定できたことを確認してからhistoryをpublishする。commitが`false`ならhistoryをpublishせず例外にする。

ただしProviderの`onCreate()`はその例外を`runCatching`で受けてprocess起動自体は継続する。このため、durable commit失敗後も後段のv1.30 history recovery、Drive bootstrap、既にWorkManagerへ登録済みのWorkerが動く余地が残っていた。

特にv1.31の`recoverStaleRun()`は互換性維持のため`apply()`を使用しているため、durable commit失敗時でも同一processのSharedPreferencesメモリ上では`running=false`へ見える可能性がある。その状態を後段がfinalized statusとして扱うと、本来publishしてはいけないhistoryを生成したり、新runの`running()`が旧progressを0へ初期化したりする可能性がある。

## v1.32の方針

startup recoveryが正常に完了しなかったprocessではDrive同期をfail closedにする。

process-wideの`GoogleDriveStartupRecoveryBarrierV132`を追加し、起動時の最上位recovery providerでresetする。v1.31 orphaned-run recoveryまたはv1.30 verification-history recoveryが失敗した場合はbarrierをblockし、そのprocessが終了するまでDrive同期を開始しない。

次processではbarrierをresetし、disk上に残った状態からrecoveryを再試行する。

## 起動順

ContentProviderの順序は変更しない。

1. `GoogleDriveOrphanedRunRecoveryProviderV131` — `initOrder=300`
2. `GoogleDriveVerificationHistoryRecoveryProviderV130` — `initOrder=200`
3. `GoogleDriveDirectSyncBootstrapProvider` — `initOrder=100`

v1.32ではこの順序に加えてbarrierを共有する。

### orphaned-run recovery失敗

`300` providerでbarrierをresetしてからv1.31 recoveryを実行する。

recoveryが失敗した場合：

- barrierをblock
- v1.30 history recoveryは実行しない
- Drive bootstrapは新しいWorkをenqueueしない
- 既に登録済みのWorkerも同期処理へ入らない
- Repositoryを直接呼ぶ経路も`statusStore.running()`より前で拒否する

### verification-history recovery失敗

v1.30 history recovery自体が失敗した場合もbarrierをblockする。

初回baselineの`markObservedDurably()`が`false`の場合はv1.32から明示的に失敗として扱う。baselineを永続化できていない状態でDrive同期を開始しない。

## 同期開始口の防御

barrierは多層で確認する。

- `GoogleDriveVerificationHistoryRecoveryV130.install()` / `reconcile()`
- `GoogleDriveDirectSyncBootstrapProvider`
- `GoogleDriveDirectSyncScheduler.setAutomaticSyncEnabled()`
- `ensurePeriodic()`
- `enqueueStartup()`
- `enqueueNow()`
- private `enqueueImmediate()`
- `GoogleDriveDirectSyncWorker.doWork()`
- `GoogleDriveDirectSyncRepository.synchronize()`

Repositoryのguardは`statusStore.running()`より前に置く。これにより最後の防壁をすり抜けても旧run countersを0へ初期化しない。

Worker内でRepository guardが競合的に発火した場合も`GoogleDriveStartupRecoveryBlockedException`は通常のDrive失敗historyへ変換せず`Result.success()`で終了し、status/historyを変更しない。

## 復旧シナリオ

### durable status commitが失敗した場合

1. v1.31 orphaned-run recoveryが失敗
2. barrier block
3. 同一processではhistory recovery / Drive syncを停止
4. process再起動
5. barrier reset
6. disk上に`running=true`が残っていればv1.31 recoveryを再試行

### status commit成功後、history appendで失敗した場合

1. finalized statusはdiskへ確定済み
2. history publishで例外
3. barrier block
4. 同一processでは新runを開始しない
5. 次processではv1.31は`running=false`のためorphan扱いしない
6. v1.30 history recoveryがfinalized statusから不足historyを補完する

これによりstatus確定とhistory publicationの間の失敗でもprogressを新runで失わない。

## 変更しないもの

- SQLite / Management DB schema
- Drive fingerprint schema
- direct status SharedPreferences field schema
- verification history JSON schema
- WorkManager unique work名
- WorkManager周期
- coalescing policy
- Drive repository page commit / fingerprint atomicity
- ContentProviderの`300 -> 200 -> 100`順
- v1.31 `recoverStaleRun()`の既存semantics

## CIで確認する内容

- barrierのblock/reset semantics
- blocked時にRepository startを拒否すること
- Repository guardが`statusStore.running()`より前にあること
- orphan recovery失敗がbarrierへ伝播すること
- v1.30 history recoveryがblocked時にskipすること
- v1.30 baseline durable commit失敗を無視しないこと
- Workerがblocked時にstatus/historyを変更せず終了すること
- Scheduler / bootstrapがblocked時に新workを開始しないこと
- 累積unit test / Kotlin compile / 3 APK build / APK integrity gate

## 実機未確認・最終総合実機試験へ繰越し

- v1.31 durable status commit失敗を実端末で再現したとき、v1.30 historyがpublishされないこと
- startup recovery失敗processで既存WorkManager jobが走っても旧progressが0へresetされないこと
- startup recovery失敗processでstartup/manual syncがenqueueされないこと
- barrier block後にprocess再起動するとrecoveryが再試行されること
- status durable commit成功後～history append前後の失敗から次processでhistoryが1件だけ補完されること
- barrier非block時の通常Drive同期が従来通り動作すること
- Android実機でContentProvider `300 -> 200 -> 100`順とbarrier visibilityが成立すること

CI成功のみでは上記を実機確認済みとは扱わない。
