# v1.33 Drive direct status durability

## 背景

v1.30～v1.32では、Drive同期のdirect statusを基準に、finalized status/historyのcrash-gap recovery、orphaned running run recovery、startup recovery failure barrierを追加した。

これらのrecoveryが正しく働くためには、direct statusそのものがprocess終了前にディスクへ永続化されていることが前提になる。

しかしv1.32までの`GoogleDriveDirectSyncStatusStore`は、通常runの以下の更新に`SharedPreferences.Editor.apply()`を使用していた。

- run開始 (`running=true` / run token / counter reset)
- page progress
- success finalization
- owned run failure finalization
- Worker側failure finalization

`apply()`はprocess内のメモリ状態を即時更新する一方、ディスク書込みは非同期である。

## 問題

### success finalization直後のprocess終了

同期自体とDB commitが完了し、process内では`running=false`になっていても、success finalizationの`apply()`がディスクへ到達する前にprocessが終了すると、次processでは旧`running=true`が見える可能性がある。

その場合、v1.31 orphaned-run recoveryは本来成功したrunを「前回process中断run」としてfailure確定する可能性がある。

### failure finalization直後のprocess終了

owned run failureまたはWorker failureがメモリ上だけfinalizeされ、history append前にprocessが終了すると、v1.30 recoveryが参照するfinalized direct statusがディスクに存在しない可能性がある。

### 0 page時点のprocess終了

run start自体がディスクへ未反映なら、次processは前processのrunning runが存在したこと自体を認識できない可能性がある。

## v1.33の方針

既存`GoogleDriveDirectSyncStatusStore`のfield schemaとlegacy methodは維持し、新しいdurable publication経路を追加する。

`GoogleDriveDirectSyncStatusDurabilityV133`を追加し、実際のDrive API同期経路では以下を`SharedPreferences.Editor.commit()`で同期永続化する。

1. run start
2. page progress
3. success finalization
4. owned run failure finalization
5. Worker failure finalization

Repository / Workerはv1.33 durable経路を使用する。

## commit失敗時

`commit()`が`false`の場合は`GoogleDriveDirectSyncStatusPersistenceException`を送出する。

同時にv1.32 `GoogleDriveStartupRecoveryBarrierV132`をblockする。

そのprocessでは、statusがディスク上でどの状態まで確定したか保証できないため、新しいDrive runへ進ませない。

Workerはこのpersistence exceptionを通常のDrive failureとしてhistoryへpublishしない。

次process起動時にv1.32 barrierがresetされ、v1.31 / v1.30 recoveryがディスク上の確定状態から再評価する。

## ordering

通常run開始:

`startup barrier check -> durable run start commit -> Drive処理`

各page:

`page import/fingerprint処理 -> durable progress commit -> next page`

成功時:

`durable success finalization commit -> Worker success history append`

通常failure時:

`durable owned-run failure finalization commit -> Worker durable failure finalization -> failure history append`

status persistence failure時:

`commit false -> barrier block -> persistence exception -> history非publish -> 同一processで新run禁止`

## 維持する仕様

- direct status SharedPreferences field schemaは変更しない
- verification history JSON schemaは変更しない
- Management DB schemaは変更しない
- Drive fingerprint schemaは変更しない
- WorkManager unique work名、周期、coalescing policyは変更しない
- v1.31 ContentProvider `300 -> 200 -> 100`順は変更しない
- v1.32 startup recovery barrierを維持する
- legacy `GoogleDriveDirectSyncStatusStore` methodは削除しない

## 残るcross-store境界

v1.33はSharedPreferences mutation自体のdurabilityを強化する版であり、SQLite page transactionとSharedPreferences progress commitを同一atomic transactionにはしない。

そのため、SQLiteのpage commitが完了した直後から`progress().commit()`を実行する直前までの極小windowでprocessが強制終了した場合、DB/fingerprintが1 page先行し、direct status progressが直前pageの値に留まる可能性は残る。

このcross-store atomicityはv1.33で「解消済み」とは扱わない。

## 実機未確認

最終総合実機試験へ以下を繰り越す。

- 0 page時点process killでdurable `running=true`が次processへ残ること
- page progress `commit()`後process killでそのcounterがorphan historyへ残ること
- success finalization直後process killで成功runがorphan failureへ誤分類されないこと
- owned failure finalization直後process killでv1.30 history recoveryが正しいfailureを補完すること
- status `commit()`失敗時に同一processのDrive同期がfail-closedになること
- persistence exception時にverification historyが誤publishされないこと
- 次processでv1.31/v1.30 recoveryがディスク状態から再評価されること
- Android実機で同期`commit()`による操作感・ANR・I/O影響が許容範囲であること
- SQLite page commit -> SharedPreferences progress commit間のcross-store crash window

CI成功のみではこれらを実機確認済みとは扱わない。
