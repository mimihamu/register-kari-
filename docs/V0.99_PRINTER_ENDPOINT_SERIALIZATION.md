# v0.99 プリンター送信経路シリアライズ

## 目的

実プリンター投入前に、手動印刷・自動印刷・再印字など複数の呼び出し元が同一TCPプリンターへ同時送信する競合を防止する。

## v0.98時点の確認結果

実コードでは以下が独立して `TcpEscPosPrinterGateway` を生成していた。

- `AutomaticPrintWorker`
- `UnifiedPrintQueueController.print()`
- `MemoryPrinterGateway` の実プリンター転送経路

各Gatewayインスタンス間には共通のhost:port排他が無く、同一プリンターに複数スレッドからTCP 9100送信が重なる余地があった。

## v0.99仕様

### 1. endpoint単位の共通送信ゲート

`PrinterEndpointSendGate` を追加し、`host.trim().lowercase():port` をendpointキーとする。

- 同一endpoint: 1送信ずつ直列化
- 異なるendpoint: 並行送信可能
- 公平ロックを使用し、待機中送信の追い越しを抑制
- endpointロックはプロセス内共有

### 2. 保護範囲

`TcpEscPosPrinterGateway.send()` の入口でpermitを取得し、以下を同一permit内で完了する。

1. TCP connect
2. output stream取得
3. ESC/POS payload write
4. flush
5. socket/stream close

呼び出し元ではなくTCP送信層を保護するため、自動Worker、手動安全印刷、責任者PIN付き強制印刷、再印字、`MemoryPrinterGateway`経由の実送信が同一規則になる。

### 3. 送信待ちタイムアウト

permit待機上限はプリンター設定の `timeoutMillis` を使用する。

上限超過時は `PrinterEndpointBusyException` とし、TCP connect前に失敗する。

この失敗は `PrinterRetrySafety` 上 `SAFE_TO_RETRY` として扱う。`WRITE_STARTED` 以降の送信結果不明とは区別する。

### 4. 既存の送信結果不明保護を維持

以下は変更しない。

- `CONNECTING` / `CONNECTED` は安全に再試行可能
- `WRITE_STARTED` / `FLUSHED` は紙が出た可能性があるため手動確認必須
- `WRITE_STARTED` 以降の失敗を自動再送しない
- 業務帳票unknown-deliveryの安全側FAILED遷移
- v0.98の古い順、1run最大20件、最初の失敗で停止、自動Worker単一実行

## 変更しない業務ロジック

- 売上計算
- 税計算
- 会計
- レシート内容
- 領収書内容
- 返品・取消
- Google Drive
- つぐレジ CD
- データ保護・復元・ロールバック

売上DBを削除・上書きする処理は追加しない。

## 自動テスト

`V099PrinterEndpointSerializationTest.kt` で以下を確認する。

- endpointキー正規化
- 同一endpointのcritical sectionが同時実行されない
- 異なるendpointは相互にブロックしない
- permit待ちタイムアウトでは送信blockへ入らない
- permit待ちタイムアウトは `SAFE_TO_RETRY`
- protected blockが例外終了してもpermitを解放
- 自動・手動・Memory経路が最終的に保護済み `TcpEscPosPrinterGateway` に集約
- destructive sales data statementを追加していない

## 実機確認

本版単独では実プリンター確認を行わない。

以下は最終総合実機試験へ繰り越す。

- 自動印刷中に手動再印字を開始した場合の直列化
- 手動印刷中に即時Workerが起動した場合の直列化
- 同一プリンターへの複数送信でESC/POSデータが混在しないこと
- permit待ちタイムアウト時に紙が排出されていないこと
- 58mm / 80mm
- 部分 / フルカット
- DK1 / DK2
- 紙切れ / カバー開 / カッター異常
- LAN切断 / 送信途中切断
- `WRITE_STARTED` 以降の障害で二重印刷しないこと
