# つぐレジ データ保全

## 対象

- SQLite `register.db` の整合性診断
- 業務データの参照・金額整合性診断
- SHA-256付き原子的バックアップ
- 復元前の営業状態・未処理データ検査
- 次回起動時のロールバック付き復元
- v1.16: WAL・migration・最終schema gateを含む復元成功境界

## 診断

`PRAGMA integrity_check`、`PRAGMA foreign_key_check`に加え、売上・明細・支払・印刷、返品・返金、保留伝票、Drive Outboxの孤立参照を確認する。売上金額と支払配賦、返品金額と返金配賦も照合する。

## バックアップ

SQLiteの一貫したスナップショットを作り、DB本体とマニフェストを`.tgbak`へ格納する。マニフェストにはアプリ版、DB user_version、作成日時、全テーブル件数、DB SHA-256を記録する。一時ファイル完成後に正式名へ切り替えるため、作成途中ファイルは正式バックアップとして扱わない。

## 復元

責任者PINを再認証し、営業中・未会計カート・保留伝票・未完了印刷・未送信Drive Outboxがなく、現在DBとバックアップDBが正常な場合だけ復元予約できる。実行中DBは直接置換せず、次回起動時に最優先Providerが現在DBをロールバック用に退避してから置換する。置換後の検査に失敗した場合は元DBへ戻す。

### v1.16 WAL-safe rollback

復元前の現行DBは `PRAGMA wal_checkpoint(TRUNCATE)` を実行し、busyでないこととcheckpoint完了を確認する。接続を閉じた後、`register.db-wal` が存在する場合は0 byteであることを確認してからmain DBをrollbackスナップショットへコピーする。スナップショットは `integrity_check`、`foreign_key_check`、SHA-256を検証してから確定し、作成に失敗した場合は現行DBを置換しない。

### v1.16 migration rollback境界

復元候補DBを正本へ配置した直後には成功確定しない。配置後のSQLite整合性・FK・必須テーブル確認に続けて、既存の `DatabaseStartupSchemaBootstrapV085.ensureBeforeUi` を復元の同じ `try/catch` 内で実行する。legacy migrationまたは後付けschema ensureが失敗した場合は、検証済みrollbackスナップショットから元DBを復旧する。

### v1.16 最終schema gate

migration後は既存の `DataProtectionManager.diagnose` と `AppUpdateDatabaseHealthCheckV089` を再利用し、SQLite整合性、外部キー、主要テーブル・列を再検証する。さらに `user_version == 4` と、印刷・営業セッション・入出金・返品・帳票印刷・精算に必要な主要indexを確認する。復元監査を書き込んだ後にも同じ最終gateを再実行し、そこまで成功した場合だけ「復元成功」を確定する。

実際の置換は `DataRestoreBootstrapProviderV086` (`initOrder=1000`) が業務用bootstrapより先に同一プロセス起動時に行う。復元予約後は既存仕様どおり、新しい業務を開始せずアプリを完全終了して再起動する。v1.16では一部Storeだけを対象にした不完全な書込みフェンスは追加しない。

## 監査

`DATA_BACKUP_CREATED`、`DATA_RESTORE_STAGED`、`DATA_RESTORE_CANCELLED`、`DATA_RESTORE_APPLIED`を`operation_audit`へ記録する。

## 実機確認

WALが残った状態からの復元、migration途中失敗、端末固有のSQLite挙動、強制終了・電源断を含む確認はコード／CI検証とは別の最終総合実機試験対象とし、未実施の事項を確認済みとは扱わない。
