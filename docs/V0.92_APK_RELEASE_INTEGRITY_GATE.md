## 目的

v0.92では、最終総合実機試験へ渡すAPKが、Gradle設定どおりのアプリ識別子・版番号・SDK・Launcher・署名を持つことを、生成済みAPKそのものからCIで検証する。

ソースコードの文字列だけを確認するのではなく、`assembleDebug` 後のAPKを `aapt2` / `apksigner` / `unzip` で直接検査する。

## CI検査

`ci/verify-apk-release-integrity.sh` が以下を実施する。

1. APKファイルが存在し、0 byteでないこと。
2. `unzip -tq` が成功し、APK ZIPが破損していないこと。
3. `aapt2 dump badging` で以下が期待値と一致すること。
   - package name
   - versionCode
   - versionName
   - minSdk
   - targetSdk
4. `launchable-activity:` が1件だけ存在すること。
5. `apksigner verify --verbose --print-certs` が成功すること。
6. APK Signature Scheme v2 が有効であること。
7. Signer #1 の証明書SHA-256が開発署名鍵と一致すること。
8. 各APKのSHA-256を `artifacts/apk-integrity-summary.txt` へ記録すること。

このゲートは `Build debug APKs` の後、APKの名称変更・Artifact uploadより前に実行する。1項目でも不一致ならArtifactを公開せずCIを失敗させる。

## データ保護

本ゲートはビルド成果物を読み取るだけであり、AndroidアプリのSQLiteや営業データにはアクセスしない。

以下は行わない。

- sales / sale_items / sale_payments の変更
- Sales Journalの削除・変更
- Google Drive JSON / sync fingerprintの変更
- SENT Outbox / quarantine / sync historyの変更
- バックアップ / ロールバックDBの変更
- 実端末へのAPKインストール

## 実機確認との関係

APK整合性ゲートは、実機試験の代替ではない。

実機確認はユーザー方針どおり**開発終盤の最終総合実機試験**でまとめて実施する。v0.92では、最終実機試験へ渡すファイル自体の取り違え・版番号違い・applicationId違い・署名違いを事前に排除する。

最終総合実機試験では引き続き以下を確認する。

- v0.91までに積み上げた800×480～1920×1080 / フォント倍率確認
- 実プリンター接続・印刷・異常復旧
- Google Drive実アカウント認証・送信
- つぐレジ CD実端末接続
- 上書き更新とDB健全性
- バックアップ・検証・復元・ロールバック
- 長時間運用・プロセス再起動・通信断などの異常系
