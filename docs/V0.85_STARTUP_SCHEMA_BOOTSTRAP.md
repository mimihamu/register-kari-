# v0.85 起動前スキーマ・ブートストラップ

## 目的

v0.84で旧SQLiteOpenHelperの破壊的DROP経路を除去したが、つぐレジの基本DB `register.db` は長期間 `DATABASE_VERSION = 4` のままで、v0.4以降に追加された多くのテーブル・列は各機能のStore初期化時に冪等作成される構成になっている。

この構成では、上書き更新・DB復元後に「アプリ自体は起動したが、特定の管理機能・領収書・再印字を初めて開いた瞬間に不足スキーマの初期化が走る」状態になる。

v0.85では、DBのuser_versionだけに依存せず、復元完了後かつUI表示前に主要な後付けスキーマを先行整備する。

## 起動順

1. `DataRestoreBootstrapProvider` (`initOrder=1000`) が保留中のDB復元を最優先で適用する。
2. 既存のContentProvider群が順次初期化される。
3. `CatalogBootstrapProvider` の先頭で `DatabaseStartupSchemaBootstrapV085.ensureBeforeUi()` を実行する。
4. スキーマ準備完了後に商品マスター同期・販売プロファイル反映へ進む。
5. その後Application / Activityが起動する。

v0.85の処理は `DATABASE_VERSION=4` の既存DBでも毎起動で実行されるため、SQLiteOpenHelperの `onUpgrade()` が呼ばれないDBも対象となる。

## 先行整備する既存Store

### 営業・管理系

`OperationsStore` の既存 `ensureSchema()` を利用する。

対象例:
- business_sessions
- cash_movements
- reversal_transactions
- reversal_payments
- reversal_items
- document_print_jobs
- settlement_reports
- operation_commit_keys
- operation_audit
- 営業日リンク列
- 返品税スナップショット列
- 点検精算完全スナップショット列

### 領収書

`ReceiptVoucherStore` の既存冪等初期化を利用する。

- receipt_voucher_batches
- receipt_voucher_issuances
- receipt_voucher_reprints

### 通常レシート再印字

`SaleReceiptReprintAuditStore` の既存冪等初期化を利用する。

- sale_receipt_reprint_requests

### 会計安全系

既存の以下を起動前にensureする。

- SaleCommitIdempotencySchema
- BusinessSessionSchema
- SettlementSnapshotSchemaV027
- DocumentPrintSafetySchema

## 最終確認

スキーマ準備後、主要テーブル・主要列が存在することをSQLiteメタデータから確認する。

確認対象列の例:
- cart_items: line_no / discount_amount / note
- sales: print_count / business_session_id / business_date
- sale_items: discount_amount / note
- held_ticket_items: discount_amount / note
- reversal_items: 税率・内外税・軽減・税記号スナップショット
- settlement_reports: opening_cash / cash_in / cash_out / snapshot_version

不足している場合は処理を継続せずfail-closedとする。欠落した状態で販売・精算・返品等を書き込むより安全側とする。

## データ保護

v0.85の新規ブートストラップ自身は以下を行わない。

- 業務テーブルのDROP
- 業務レコードのDELETE
- sales / sale_items / 領収書 / 再印字監査のUPDATE
- Sales Journal / Drive JSON / sync fingerprint / SENT Outbox / 隔離・同期履歴の削除・置換

実際のスキーマ作成・列追加は、既に各機能で利用されている冪等 `CREATE TABLE IF NOT EXISTS` / guarded ALTER処理を先行実行するだけとする。

## 実機確認が必要

- v0.4相当DBからv0.85への上書き更新
- v0.84 DBからv0.85への上書き更新
- 復元予約DBが先に適用され、その後スキーマ準備されること
- 既存売上・保留・商品・領収書・再印字履歴が保持されること
- 初回起動後、営業開始、返品取消、点検精算、領収書、再印字画面を開けること
- ストレージ容量不足などでスキーマ準備に失敗した場合に部分運用へ進まないこと
- 大量売上DBで起動時間が実運用上許容範囲であること

CI・ユニットテスト成功のみで実機確認済みとは扱わない。
