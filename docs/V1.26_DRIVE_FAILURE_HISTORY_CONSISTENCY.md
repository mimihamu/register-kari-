# v1.26 Drive failure history consistency

## 問題

v1.23〜v1.25で、Drive API同期のstatusは次の2種類の失敗を正しく区別できるようになった。

- repository開始前の認可等の失敗: 今回runの件数は0
- 1ページ以上commit後の失敗: 最後にcommit済みの確認/新規/重複/隔離件数を保持

しかし同期運用ダッシュボードの検証履歴は、Drive API失敗時でも常に `listed/imported/duplicate/rejected=0` を保存していた。

このため、直近statusと監査用履歴で同じ失敗runの件数が食い違っていた。

## 修正

`GoogleDriveFailureVerificationRecordV126` を追加した。

Drive API failureでは以下の順序で処理する。

1. 外側 `GoogleDriveDirectSyncStatusStore.failed(...)` を実行
2. v1.25のowned-run markerを消費し、status件数を最終確定
3. `statusStore.load()` で確定済みstatusを再読込
4. その `listed/imported/duplicate/rejected` を検証履歴へ保存
5. failure recordの `errorCount` は `maxOf(status.errorCount, 1)` とし、attempt失敗を必ず1件以上として記録

これにより、preflight failureでは0件、途中commit後failureではcommit済み件数が履歴にも残る。

互換フォルダ方式にはDriveのページ単位checkpointがないため、例外で処理自体が完了しなかった場合は従来通りgeneric failure（件数0 / error1）を維持する。

## 保証する性質

- Drive API失敗履歴と確定済みdirect statusの件数が一致する。
- v1.25のpreflight reset結果を履歴にも反映する。
- v1.23のcommit済みpartial progressを失敗履歴にも反映する。
- 成功履歴、隔離1件再試行履歴、互換フォルダ成功履歴の既存仕様は変更しない。
- DB schema変更なし。履歴SharedPreferences形式も変更なし。

## テスト

`V126DriveFailureHistoryConsistencyTest` で以下を固定する。

- partial Drive failureでcommit済み件数が履歴recordへ移ること
- preflight failureの0件statusが0件履歴になること
- `statusStore.failed()` の後に `statusStore.load()` し、その後record生成すること
- failure recordは最低1 errorを記録すること
- 互換フォルダfailureは従来のgeneric failure semanticsを維持すること
