# v0.83 復元Bootstrap起動順序安全化

## 目的

復元予約済みDBを、カタログ・Outbox・印刷復旧・Customer Display等の起動時初期化がSQLiteを利用する前に確実に適用する。

Androidの同一プロセスContentProviderは `android:initOrder` の数値が大きいものから初期化される。v0.82以前は `DataRestoreBootstrapProvider=10`、他Bootstrap Providerが100〜150であり、復元処理が後になる設定だった。

## v0.83変更

- `DataRestoreBootstrapProvider` の `android:initOrder` を `1000` へ変更
- 現在の他自前Bootstrap Provider（最大150）より必ず先に起動
- 復元予約がある場合は `PendingRestoreApplier.applyIfPresent()` が先に完了してから後続Providerへ進む
- 復元成功後は既存の整合性検査と `DATA_RESTORE_APPLIED` 監査を維持
- 復元失敗時は既存のrollback DBへ戻す処理を維持
- 復元予約がない通常起動はファイル存在確認だけで通過

## 回帰防止

`V083RestoreBootstrapOrderTest` がAndroidManifest内のProviderを列挙し、`DataRestoreBootstrapProvider` のinitOrderが他Providerより常に大きいことを検証する。

将来Bootstrap Providerを追加する場合も、restoreの順序を追い越す値を設定するとテストで失敗する。

## 変更しないもの

- バックアップ形式 `TSUGUREGI_BACKUP_V1`
- DB SHA-256検証
- SQLite integrity_check
- 必須テーブル検査
- 責任者PIN
- 復元ブロッカー判定
- 売上SQLite既存行
- Sales Journal
- Google Drive JSON
- sync fingerprint
- imported sales
- SENT Outbox
- quarantine / sync history
- 税・インボイス計算

## 実機確認

CI成功は実機確認済みを意味しない。以下を実端末で確認する。

- 復元予約→アプリ完全終了→再起動で復元が適用されること
- 復元後にCatalog / Outbox / 印刷復旧等が復元後DBを参照すること
- 復元DB破損時に元DBへrollbackすること
- 復元予約なしの通常起動
- v0.82→v0.83上書き更新
- 強制終了・端末再起動を挟む復元
