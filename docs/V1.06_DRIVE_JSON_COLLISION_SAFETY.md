# v1.06 Drive JSON 同名衝突の非破壊化

## 背景

つぐレジの売上同期は、SQLiteへ確定した売上を Sales Journal / sync_outbox へ記録し、ローカルstaging JSONを経由してGoogle Drive・USB・端末フォルダ等のAndroid Storage Access Framework送信先へ確定JSONとして保存する。

v1.05以前の外部送信処理には、送信先に同一object keyの確定JSONが既に存在し、サイズまたはSHA-256が今回のstaging JSONと一致しない場合、その既存ファイルを削除して今回のJSONへ置き換える経路があった。

売上データの確定JSONは自動削除・自動上書きしない方針のため、この挙動をv1.06で廃止する。

## v1.06の規則

送信先に同名の確定対象が存在する場合は次のように扱う。

1. 同名対象が通常ファイルである。
2. ファイルサイズがstaging JSONと一致する。
3. SHA-256がstaging JSONと一致する。

3条件をすべて満たす場合のみ、既に同一JSONが確定済みと判断し、重複送信成功として `SENT` にできる。

それ以外は `OutboxDestinationCollisionException` とする。

- サイズが異なる
- SHA-256が異なる
- 同名フォルダが存在する

これらの場合、既存の確定対象を削除・上書きしない。

## 衝突時の状態

同名衝突はネットワーク再試行で自然解消する種類の失敗ではないため、自動10回再試行へ入れず、その送信レコードを即時 `FAILED` とする。

- 既存JSON: 保持
- ローカルstaging JSON: 保持
- sync_outbox: 保持
- Sales Journal: 保持
- SQLite売上: 変更しない
- 自動再試行: 行わない
- 失敗通知・監査: 記録する

監査eventは `SYNC_OUTBOX_EXTERNAL_COLLISION` とする。

管理者が送信先を確認し、外部で衝突原因を解消した後は、既存の「失敗を再試行」操作で `FAILED` を再投入できる。アプリ自身が既存の確定JSONを削除して解消することはしない。

## `.partial` の扱い

`<final>.json.partial` は確定JSONではなく、つぐレジ自身が送信途中に作成する未確定一時ファイルである。

前回処理で残留した同名 `.partial` の回収・削除は従来通り維持する。また、今回の送信処理中に新規作成し、確定前に失敗した一時ファイルや今回処理で作成した未確定final候補のcleanupも維持する。

このcleanupは送信開始前から存在していた確定JSONの削除とは区別する。

## 売上確定後の耐障害性確認

v1.06の事前スキャンで、通常会計確定時は次が同一SQLite transactionに含まれることを再確認した。

- 売上header/items/settings/payments
- operation idempotency
- receipt print job
- Sales Journal / sync_outbox
- work cart clear
- sale commit key bind

したがって、売上DBだけ確定して印刷queueまたは同期outboxが欠落する別経路は今回確認されなかった。

また、起動時に残留 `PRINTING` を無条件再送せずFAILEDへ回収する既存の二重印刷防止も変更しない。

## 非変更範囲

- 売上計算
- 税マスタ、内税・外税、軽減税率、税記号
- 値引・割引
- 支払配賦
- 会計冪等キー
- レシート/領収書内容
- プリンタ通信・印刷queue
- Customer Display通信
- Z精算の現金実査必須化
- v1.04データ保護

## 実機・実アカウント確認

Google Drive等の実Storage Access Framework providerで、以下は最終総合実機試験へ繰り越す。

- 同一JSONが既存の場合に重複成功となること
- 同名・異内容JSONが既存の場合に既存JSONが変化しないこと
- 衝突が即FAILEDとして見えること
- 失敗通知・監査表示
- 外部で衝突解消後の手動再試行
- provider固有のrename/create挙動

実アカウントで未確認のため、確認済みとは扱わない。
