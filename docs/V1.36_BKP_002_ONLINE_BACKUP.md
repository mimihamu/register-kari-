# v1.36 BKP-002 取引中バックアップ

正式仕様 v2.5 `BKP-002` を正本とする。Issue #137 #40 の旧「自動バックアップ保持期間」は番号・意味がずれており、保持世代 7～365 / 初期30世代は `BKP-001` 側で対応済み。

## 正式要件

- 取引中のバックアップは、SQLite online backup 等のライブDB向け手段を用い、販売を長時間停止しない。
- 10,000取引データで、販売中にバックアップを実行して30秒以内を目標とする。

## 実装

1. SQLite が対応する端末では既存の `VACUUM INTO` を最優先する。これはライブDBの一貫した別ファイルsnapshotを作る経路で、販売DBそのものを上書きしない。
2. Android API 26～28等、SQLiteが `VACUUM INTO` 非対応の場合は既存V104の WAL checkpoint → EXCLUSIVE → WAL再確認というcrash-safety fenceを維持する。
3. 旧SQLite fallback のEXCLUSIVE中ファイルコピーだけを `DataProtectionOnlineBackupV136.copyWithinWriterBlockBudget()` に置換し、2,000msを超えた場合はbackupを失敗させる。販売書込みを無期限に待たせるより、backup失敗を選ぶ。
4. timeout時の不完全snapshotは削除し、`AutoBackupWorker` の既存failure経路から監査・通知へ流す。
5. `V104DataProtectionCrashSafetyTest` のcheckpoint/lock/WAL fence契約を維持し、`V140DataProtectionOnlineBackupTest` で有界停止・正式性能目標・modern/fallback順序を固定する。

## 検証区分

ソース/ユニットテスト/Android compile/APK buildはCIで検証する。

以下は実機性能に依存するため `実機未確認` とする。

- 実端末で10,000取引を投入した状態の販売並行backupが30秒以内
- API 26～28相当端末で `VACUUM INTO` 非対応fallbackが2秒以内に完了または中止し、販売操作が長時間停止しないこと
- OEM SQLite差異、低速ストレージ、Doze/高負荷時の実測

## 既存安全性との関係

- `BKP-001` のAES-256-GCM envelope、manifest/SHA-256、SQLite integrity_checkは変更しない。
- V104のWAL再競合検知とatomic replaceは変更しない。
- snapshot作成後の整合性検査・暗号化・archive検証は販売DBロック外で行う。
