# v1.07 SAF object key 保存名整合性

## 背景

つぐレジの外部売上同期は、SQLiteへ確定済みの売上をローカルstaging JSONへ生成し、Android Storage Access Framework（SAF）を通じてGoogle Drive・USB・端末フォルダ等へ保存する。

v1.06では、送信先に同一object keyの確定JSONが既に存在する場合、通常ファイル・同一サイズ・同一SHA-256の3条件がそろったときだけ重複成功とし、それ以外は既存JSONを削除・上書きせず衝突FAILEDとした。

一方、SAFのDocumentsProviderは、`createDocument` / `renameDocument` に指定された表示名をプロバイダ内部の制約や重複回避のため変更して返す場合がある。v1.06は返却URIのサイズとSHA-256は確認していたが、そのURIの実際の `COLUMN_DISPLAY_NAME` が要求したobject key末尾名と完全一致していることまでは確認していなかった。

このため、例えば `sale.json` を要求したのにプロバイダが `sale (1).json` として確定した場合、内容が正しければ送信成功扱いになり得る余地があった。

## v1.07の規則

SAF経由で新規作成またはrenameしたディレクトリ／JSONは、返却URIから `DocumentsContract.Document.COLUMN_DISPLAY_NAME` を再取得し、要求名と完全一致する場合だけ後続処理へ進める。

完全一致の条件は文字列の完全一致とする。

- `sale.json` → `sale.json`: 許可
- `sale.json` → `sale (1).json`: 拒否
- `sale.json` → `SALE.JSON`: 拒否
- 表示名取得不可: 拒否

プロバイダによる自動変名を正常なobject key確定とは扱わない。

## 変名検出時の安全動作

変名された対象は、今回の送信処理が新規作成またはrenameしたアプリ所有の未確定対象であるため、その対象だけを削除して回収する。

その後 `OutboxProviderNameMismatchException` を送出する。この例外はv1.06の `OutboxDestinationCollisionException` を継承し、既存の衝突安全経路へ合流する。

- sync_outbox: `FAILED`
- 自動再試行: 行わない
- ローカルstaging JSON: 保持
- Sales Journal: 保持
- SQLite売上: 変更しない
- 監査: `SYNC_OUTBOX_EXTERNAL_COLLISION`
- 管理者が原因を解消した後の手動再試行: 維持

送信先に処理開始前から存在していた確定JSONは削除・上書きしない。v1.06の同名衝突非破壊ルールを維持する。

## rename失敗との区別

通常のrename例外は従来どおりcopy-to-finalフォールバックを許可する。

ただし、rename自体は成功したものの返却先の表示名が要求名と異なる場合は、通常のrename失敗として握りつぶさない。変名を検出した時点で `OutboxProviderNameMismatchException` をそのまま上位へ送出し、別名ファイルを送信成功扱いにしない。

copy-to-final経路で `createDocument` が別名を返した場合も同じ完全一致検査を行う。

## 非変更範囲

- 売上計算
- 税計算・税マスタ・内税／外税・軽減税率
- 値引・割引
- 支払配賦・会計冪等性
- Z精算
- レシート／領収書内容
- プリンタ通信・印刷queue
- つぐレジ CD通信
- バックアップ／復元
- v1.06の既存確定JSON非破壊ルール

## 実機・実アカウント確認

以下は最終総合実機試験へ繰り越す。

- Google Drive実アカウントで要求名どおり作成される通常送信
- 実providerでrenameが成功する経路
- rename非対応providerでcopy-to-finalへ移る経路
- 重複名等によりproviderが自動変名するケースを再現できる場合のFAILED化
- 変名されたアプリ所有ファイルだけが回収され、既存確定JSONが保持されること
- 外部で原因解消後の手動再試行
- provider固有の `COLUMN_DISPLAY_NAME` / create / rename挙動

実アカウント・実providerでは未確認のため、確認済みとは扱わない。
