# v1.03 つぐレジ CD 接続liveness・半断線回収

## 目的

v1.02でPOS側WebSocket送信をCD接続ごとに分離し、1台の遅い/半切断CDがPOS pollerや別CDの送信を止めないようにした。

v1.03では、その上で長時間運用時に残り得る「TCP接続自体はOS上に残っているが、相手と実際には通信できない」半断線をPOS側から回収できるようにする。

## v1.02時点の課題

`CustomerDisplayWebSocketServer` は以下が無期限待ちだった。

- TCP accept後、HTTP/WebSocket handshake要求を受信するまで
- WebSocket接続成立後、次のクライアントframeを受信するまで

Android/OSのTCP keepaliveだけでは、Wi-Fi切替やAP障害等の状態によって古いsocketが長時間残る可能性がある。

またv1.02の非同期text writerはPOS pollerを保護する一方、古いsocketへのOS writeが長時間止まった場合、その接続専用writerも残り得る。

## 実装

### 1. handshake timeout

TCP accept直後は `5,000ms` のread timeoutを設定する。

WebSocket upgrade要求を5秒以内に完了しない接続は閉じ、未完了handshakeがサーバthreadを無期限に保持しない。

### 2. 接続後liveness check

WebSocket handshake成功後はread timeoutを `15,000ms` に変更する。

frame境界でread timeoutが発生した場合、即切断はせず、最後にtransport activityが確認できた時刻を見る。

### 3. transport activity

以下のどちらかをtransport activityとして扱う。

- CDから完全なWebSocket frameを受信した
- POSからtext/control frameを正常に `flush()` できた

このため、販売中にPOSから商品・合計等を頻繁に送信し、CD側heartbeat Pingが発生しない状態でも、正常送信が続いている接続を誤って切断しない。

### 4. stale判定

最後のtransport activityから `45,000ms` 以上経過した場合のみ、その接続をstaleとして閉じる。

既存CDクライアントは15秒受信が無い場合にWebSocket Pingを送るため、正常なアイドル接続ではCD→POSのheartbeatがactivityを更新する。

半断線でPOS→CD writeもCD→POS heartbeatも成立しない場合は、read側liveness確認からsocketをcloseできる。write threadがsocket write中でも、liveness判定そのものはwriter lockを取得しない。

## 維持する仕様

- v1.02の接続別非同期送信
- pending snapshot最新1件へのcoalesce
- token認証
- 接続直後の最新snapshot送信
- `sequence` / `serverInstanceId` による重複除外
- CD側自動再接続
- Ping/Pong
- 販売・税・値引・印刷・Google Drive・データ保護仕様
