# v1.31 Drive orphaned run startup recovery

## 背景

v1.21以降、Drive API同期はsingle-flightとrun-token ownershipを持ち、v1.23～v1.30でpartial progress、failure ownership、history consistency、WorkManager history、history競合、history crash recoveryを順に強化した。

ただしAndroid processがDrive同期中に終了した場合、SharedPreferencesには`running=true`と最後にcommit済みpageまでのprogressが残り得る。

v1.30のverification-history recoveryはfinalized direct statusのみを対象とし、`running=true`は意図的に合成しない。

## 問題

新しいprocessが起動した時点では、前processのin-memory single-flight lockやrepositoryは存在しないため、persisted `running=true`は実行中ではなくorphaned runである。

しかしv1.30までの起動順では、history recoveryが`running=true`を無視した後、Drive bootstrapがWorkManagerをscheduleする。

新しいWorkerがrepositoryへ入ると`statusStore.running()`が新runのcounterを0へ初期化するため、前processが最後にpage commit後へ保存したlisted/imported/duplicate/rejected等のprogressと、その中断監査情報を新run開始前に失う可能性がある。

## v1.31の修正

`GoogleDriveOrphanedRunRecoveryProviderV131`を追加する。

起動順は次の通り。

1. v1.31 orphaned-run recovery provider: `initOrder=300`
2. v1.30 verification-history recovery provider: `initOrder=200`
3. existing Drive WorkManager bootstrap provider: `initOrder=100`

Android process起動時、v1.31 providerがpersisted direct statusを読み、`running=true`の場合だけ前process由来のorphaned runとして中断確定する。

中断確定ではdirect statusと同じSharedPreferencesへ、既存`recoverStaleRun()`と同じfield semanticsを専用のdurable経路で書き込む。

- `running=false`
- run token除去
- owned failure pending marker除去
- `lastCompletedAt`を中断確定時刻へ更新
- failure categoryを`UNKNOWN`
- page commit後に保存済みのprogress counterはresetしない

起動復旧ではWorkManager bootstrapより前に中断確定を永続化する必要があるため、通常UI用の非同期`apply()`ではなく`commit()`を使用する。`commit()`が失敗した場合はhistoryを先行生成せず、復旧処理を失敗として終了する。

その直後にfinalized statusを読み直し、`GoogleDriveVerificationHistoryRecoveryPolicyV130.recordFromFinalizedStatus()`の既存semanticsで監査recordを生成する。

- listed/imported/duplicate/rejectedを保持
- failureなので`success=false`
- history errorCountは最低1
- messageは「前回process中断runを起動時に中断確定」と明示

recordはv1.29のserialized history storeへappendしてからv1.30 providerとWorkManager bootstrapへ進む。

## なぜ起動時のrunning=trueを中断扱いにできるか

ContentProviderは新しいapplication processの初期化時にActivity/WorkManagerより先に生成される。

v1.31 provider実行時点では、この新process内でDrive repository runは開始していない。したがってpersisted `running=true`は現在processが所有するactive runではなく、前process終了時に残った状態として扱える。

通常process内で実行中のrunを途中から奪う処理は追加しない。

## v1.30との連携

v1.31がorphaned runをfinalizeしてhistoryへappendした後、v1.30 providerが起動する。

v1.30 recoveryは同じfinalized statusに対応するhistoryが既に存在すれば重複追加せず、watermarkを進める。これにより起動時中断recordとcrash-gap recoveryが重複しない。

初回v1.30 watermark baselineの場合でも、v1.31が先にhistoryをappend済みなので中断監査recordは残る。

## 維持する保証

- v1.21 Drive sync single-flight / run-token ownership / immediate work coalescing
- v1.22 Drive import + fingerprint atomic commit
- v1.23 page commit後のpartial progress保持 / 新run counter reset
- v1.24 importer compatibility signature / transport fingerprint reset境界
- v1.25 failure progress ownership
- v1.26 finalized failure statusとhistory件数一致
- v1.27 WorkManager verification history
- v1.28 foreign/newer direct statusのfailure history誤帰属防止
- v1.29 history mutation serialization
- v1.30 finalized-status/history crash-gap recoveryとexplicit clear preservation

## 変更しないもの

- SQLite / Management DB schema
- Drive fingerprint schema
- direct status SharedPreferences field schema
- verification history JSON schema
- WorkManager unique work名・周期・coalescing policy
- Drive repositoryのpage commit / fingerprint atomicity
- Compatibility Folder semantics

## recovery中の再process終了

v1.31はorphaned direct statusの中断確定を同期`commit()`した後にhistory storeへrecordをappendするため、status確定前にhistoryだけが先行する順序にはしない。

status確定後からhistory append完了前に再度processが終了した場合は、v1.30のfinalized-status/history crash-gap recoveryが次回起動で補完対象にできる。status/historyを同一DB transactionへ統合するschema変更は行わない。

## テスト

`V131DriveOrphanedRunRecoveryTest`で以下を確認する。

- persisted `running=true`のみprocess-start recovery対象になる
- finalized statusはorphan扱いしない
- recovered statusから生成するhistoryがcommit済みprogressを保持する
- recovered historyはfailureとしてerrorCountを最低1にする

CI source gateではproviderの`initOrder=300 > 200 > 100`、`finalizePersistedRunDurably -> load finalized -> append history`の順序、durable finalizeが`commit()`を使用することを確認する。

## 実機未確認・最終総合実機試験へ繰越し

- 1ページcommit後にprocess killし、再起動時にそのprogressが中断履歴へ残ること
- 起動直後のWorkManagerが旧run progressを0へ上書きする前にrecoveryが完了すること
- 0ページ時点でprocess killしたorphaned runの履歴表示
- v1.30 crash-gap recoveryとの重複record非発生
- recovery直後に再度process killした場合の再起動挙動
- Android実機でContentProviderの`300 -> 200 -> 100`順が成立すること

CI成功のみでこれらを実機確認済みとは扱わない。
