# v1.36 印刷文書の電子ジャーナル／保持期間

正式仕様 v2.5 §16.9 / §16.10 に対し、印刷結果安全化に続いて「構造化電子ジャーナル」「payloadJson / renderedHash」「印刷エラー詳細ログ保持」を補完する。

## 実装方針

- 売上確定時、`sales_journal.payload_json` の既存税snapshotを壊さず、`printDocument` を追加する。
- `printDocument` は文書種別、営業日、発行時刻、担当者、店舗／登録番号、商品明細、税snapshot、合計、支払、釣銭を持つ。
- 自動レシートの `print_jobs.payload_json` は売上確定と同一SQLite transaction内で同じ構造化snapshotを保存する。
- `print_jobs` / `document_print_jobs` に `payload_version`, `payload_json`, `rendered_hash` を後方互換で追加する。
- 売上以外の帳票は、既存の全insert経路を漏れなく捕捉するSQLite triggerで `print_document_journal_v136` へ追記する。
- `print_document_journal_v136` は `document_type`, `reference_id`, `source_job_id`, `paper_width_mm`, exact `rendered_text`, `rendered_hash`, `created_at` を別列で保持する。ESC/POS生バイトだけを正本にしない。
- 実送信直前の最終バイト列SHA-256を `rendered_hash` として保存する。売上レシートと業務帳票の双方で送信前に確定する。
- `last_error` の変更は `print_error_journal_v136` へ追記し、エラーが上書きされた場合も履歴を失わない。

## 保持

- 電子ジャーナル最低保持: 730日。
- 印刷エラー詳細最低保持: 365日。
- 現行実装は通常クリーンアップ対象外で、これら3表 (`sales_journal`, `print_document_journal_v136`, `print_error_journal_v136`) を削除する通常APIを持たない。
- `print_journal_retention_policy_v136` に最低保持値と `ordinary_cleanup_allowed=0` をDB上にも記録する。
- プリンター診断用の短期履歴 (`printer_status_history` 等) は補助診断データであり、この正式な印刷エラー詳細ログの正本ではない。
- バックアップはSQLite DB全体を対象とするため、上記表もDBバックアップに含まれる。

## 後方互換

既存 `sales_journal` のトップレベル税項目は残す。管理アプリ／同期側が参照する既存キーを変更せず、`printDocument` を追加する方式とした。

既存の `print_jobs` / `document_print_jobs` は起動時にschemaを補完する。過去の業務帳票行は `print_document_journal_v136` へbackfillし、過去の売上印刷ジョブは売上ID／紙幅を持つ構造化reference envelopeでbackfillする。

## 実機確認

本変更はDB snapshot／hash／保持ポリシーであり自動試験可能。実紙との完全一致については、58/80mm、EPSON状態取得、用紙切れ／カバーオープン、LAN切断など既存のプリンター実機確認と合わせて確認する。これらは **実機未確認** のまま扱う。
