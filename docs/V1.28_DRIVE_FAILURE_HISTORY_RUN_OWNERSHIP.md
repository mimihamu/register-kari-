# v1.28 Drive failure history run ownership

## 背景

v1.25では、Drive API同期のdirect statusについてrun ownershipを整理し、repository所有runの途中失敗ではcommit済みprogressを保持し、repository開始前のpreflight failureでは旧run件数を0へresetするようにした。

v1.26では、そのfinalized direct statusを同期検証履歴へ反映し、direct statusとfailure historyの件数を一致させた。

v1.27では、手動同期だけでなくWorkManager経由の同期も同じ検証履歴へ保存するようにした。

一方、failure history生成時には「読み直したdirect statusが、いま履歴化しようとしているfailure自身のfinalized statusであるか」を確認していなかった。

## 問題

別のDrive同期runが`running=true`でdirect statusを所有している最中に、別経路の同期がGoogle認可失効などでrepository開始前に失敗した場合、v1.25の`statusStore.failed(...)`はactive runを保護するためstatusを書き換えずにreturnする。

このdirect status側のownershipは正しい。

しかし、その直後にfailure history側が`statusStore.load()`した結果を無条件でコピーすると、activeな別runのlisted/imported/duplicate/rejected件数を、失敗したpreflight runの監査履歴として誤って記録できてしまう。

同様に、failure処理の間により新しい成功状態や異なるfailure categoryの状態を読み込んだ場合も、別runの件数を誤帰属する可能性がある。

## v1.28の修正

`GoogleDriveFailureVerificationRecordV126.fromDirectStatus(...)`にfinalized failure ownership判定を追加する。

件数をfailure historyへ関連付けてよい条件は次のすべてを満たす場合とする。

- `status.running == false`
- `status.lastFailureCategory != null`
- `status.lastFailureCategory == GoogleDriveSyncErrorPolicy.classify(error)`

条件を満たす場合はv1.26 semanticsを維持し、finalized direct statusのcommit済み件数を履歴へ保存する。

条件を満たさない場合は、そのdirect statusを当該failureの所有状態とみなさず、DRIVE_APIのgeneric failureとして件数を0にして保存する。履歴messageには、別同期runのstatusであるため件数を関連付けていないことを残す。

## 維持する保証

- v1.21 Drive sync single-flight / run-token ownership / immediate work coalescing
- v1.22 Drive import + fingerprint atomic commit
- v1.23 page commit後のpartial progress保持 / 新run counter reset
- v1.24 importer compatibility signature / transport fingerprint reset境界
- v1.25 preflight failureの旧件数reset / owned-run failureのcommit済みprogress保持
- v1.26 finalized failure statusとfailure historyの件数一致
- v1.27 WorkManager成功・失敗の検証履歴保存

matching finalized failureでは、従来どおりpartial failureのcommit済み件数を保持する。

## 変更しないもの

- SQLite / Management DB schema
- Drive fingerprint schema
- direct status SharedPreferences schema
- verification history SharedPreferences schema
- WorkManager unique work名・周期・coalescing policy
- Drive repositoryのsingle-flight / run-token ownership
- Compatibility Folderのhistory semantics

## ownership判定の境界

v1.28は、activeな別run、より新しいsuccess status、異なるfailure categoryのstatusから件数を誤帰属する問題を防ぐ。

現行status schemaにはfailureを一意に対応付ける永続run tokenがfinalized後まで残らないため、時間的に別runであっても同じfailure categoryが連続したケースまで完全なtoken一致で識別する変更は行わない。そこまでの厳密な永続ownershipが必要になった場合は、status/history schemaを含む別versionの設計対象とする。

## テスト

`V128DriveFailureHistoryRunOwnershipTest`で以下を回帰確認する。

- active foreign runの件数をpreflight failureへ関連付けない
- newer successful statusの件数をolder failureへ関連付けない
- different failure categoryのstatusを所有failureと判定しない
- matching finalized failureではcommit済みprogressを従来どおり保持する

既存`V126DriveFailureHistoryConsistencyTest`も、実際のfailure categoryと一致するerror型を使ってv1.26保証を継続確認する。

## 実機未確認・最終総合実機試験へ繰越し

- WorkManager同期中に手動同期側でGoogle認可失効が発生した場合、foreign run件数がfailure historyへ混入しないこと
- 手動同期中にWorkManager preflight failureが発生した場合の履歴表示
- partial failureでmatching finalized failureのcommit済み件数が実Driveでも保持されること
- WorkManager retryと手動同期が近接した場合の履歴時系列
- アプリ再起動後の履歴永続化

これらはCI成功のみで確認済みとは扱わない。
