# v1.02 つぐレジ CD 送信分離・実機通信安全化

## 目的

つぐレジ本体の顧客表示 WebSocket サーバーは、v1.01 まで `CustomerDisplayPoller` の更新処理から各接続へ同期的に `OutputStream.write()` していた。

TCP の write には Android/Java `Socket.soTimeout` が適用されないため、LAN 切断途中・受信停止・端末フリーズなどで 1 台の顧客表示への write が停滞すると、次の問題が起き得る。

- 300ms 周期の顧客表示 poller が停止する
- 正常な別の つぐレジ CD へも後続 snapshot が届かない
- 商品追加、小計、会計完了、お釣り表示の更新が遅延する
- 切断端末向けの送信を単純に非同期キューへ積むだけでは、古い SALES snapshot が無制限に蓄積し得る

## v1.02 の変更

`CustomerDisplayLatestSendDispatcher` を追加し、接続ごとの text frame 送信を POS の poller から分離した。

### 正常時

1. `CustomerDisplayRuntime.publish()` が最新 snapshot を更新する
2. `CustomerDisplayWebSocketServer.broadcast()` は各接続の dispatcher へ snapshot を渡す
3. dispatcher は専用 executor 上で WebSocket text frame を送信する
4. poller は socket write 完了を待たず次の監視へ戻る

### 遅い / 停止した CD がある場合

- write 実行中の接続には後続 snapshot を無制限に積まない
- pending slot は 1 件のみ
- 新しい snapshot が来るたび pending slot を最新値で置換する
- writer が復帰したら、その時点で最新の snapshot を送信する
- 他の接続は独立した writer task で送信を継続する

このため、古い SALES 表示を順番に再生する backlog を作らず、正常な CD を巻き込まない。

### write 失敗

socket write が例外終了した接続は dispatcher を閉じ、transport socket を閉じる。以後その dispatcher は新しい snapshot を受け付けない。既存の client reader/finally 経路で接続一覧から除去される。

## 維持する既存仕様

- WebSocket path: `/customer-display/v1`
- pairing token 認証
- 接続直後に最新 snapshot を送信
- `sequence` / `serverInstanceId` による重複・逆順 snapshot 除外
- CD 側の自動再接続
- Ping/Pong
- STANDBY / SALES / ACCOUNTING / COMPLETE / DISCONNECTED
- COMPLETE 表示時間設定
- 売上・税・印刷・Google Drive の業務ロジック

## 自動テスト

`V102CustomerDisplaySendIsolationTest` で次を確認する。

- writer を意図的に停止しても producer の `offer()` が待たされない
- 停止中に second / third を投入すると first の後は最新 third のみ送られる
- 1 台の writer が停止していても別 dispatcher は送信できる
- write 失敗後は新しい snapshot を受け付けない
- close 後は新しい snapshot を受け付けない

## 実機確認

以下は自動テストでは確認済みとしない。最終総合実機試験で確認する。

- つぐレジ実機 + つぐレジ CD 実機の同一LAN接続

- 小計 / 会計完了 / お釣り表示
- CD の Wi-Fi OFF / ON と自動復旧
- POS 側 LAN 瞬断と復旧
- 2 台以上の CD のうち 1 台だけを切断した場合に、正常端末が更新を継続すること
- COMPLETE → STANDBY の遷移
- 長時間連続接続
