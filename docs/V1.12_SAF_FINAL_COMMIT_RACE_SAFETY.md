# v1.12 SAF確定JSONコミット競合安全化

## 背景

v1.11までで、SAF / DocumentsProviderへの外部JSON送信について、同名衝突、Provider自動変名、同名複数候補、query不能、メタデータquery不能、rename例外の誤フォールバックを安全側に扱うようにした。

一方、`deliverOne()` は最初に確定JSONが存在しないことを確認してから `.partial` を作成・検証し、その後rename/copyで確定する。この時間中に別プロセスや外部クライアントが同じ確定JSON名を作成すると、最初の確認結果だけでは競合を検出できない。

## v1.12 方針

### 確定直前の再照合

`.partial` のサイズ・SHA-256検証完了後、rename/copyを開始する直前に確定JSON名を再検索する。

- 見つからない: 確定処理へ進む。
- 1件あり、サイズ・SHA-256がローカルJSONと一致: 既に同内容が確定済みとして、アプリ自身の `.partial` を削除し送信済み扱いとする。
- 1件あり、内容不一致またはdirectory: 衝突として停止し、既存項目は変更しない。
- 同名複数: v1.08の衝突経路。
- query不能: v1.09のretry経路。

### 確定直後の再照合

rename/copy後に確定URIのサイズ・SHA-256を検証したうえで、確定JSON名を再検索する。

- 同名項目が見えない: 確定可視性を保証できない一時障害として成功扱いせずretryする。
- 同名複数: v1.08の衝突経路。
- 1件だけ見えるがdocument IDが今回確定したURIと異なる: 競合衝突として停止する。
- 今回確定したdocument IDと一致: 送信成功を確定できる。

確定直後の照合に失敗した場合は、`committedUri` として追跡しているアプリ自身の確定オブジェクトだけをcleanupする。検索で見つかった他者の既存項目は削除しない。

## 残る競合窓

DocumentsProvider側に原子的な「同名が存在しない場合のみrename/create」の汎用APIはないため、最終照合完了後に外部クライアントが変更する可能性そのものは排除できない。v1.12では、アプリが制御できる確定処理の前後を再照合し、送信成功判定時点での一意性とdocument identityを確認する。

## 実機確認

実Google Drive / DocumentsProviderで、確定直前・直後に同名JSONを発生させた場合の非破壊停止、同内容競合の重複成功、異内容競合、同名複数、Provider可視性遅延は最終総合実機試験で確認する。
