# v1.36 BKP-006 / BKP-018 復元後同期・同期再構築

正式仕様 v2.5 の BKP-006「同期再構築」および BKP-018「復元後同期」に対する実装記録。

## 正式要件の解釈

BKP-006 の「復元時に Drive index とローカル DB を照合し、未送信・未取込を再生成。再送しても二重取込なし」は、同期方向ごとに責任を分ける。

- **未送信**: つぐレジ本体が、復元DBの `sales_journal` と `sync_outbox` / Drive送信indexを照合し、不足outboxを再生成する。復元後のDirect Drive処理で `duplicateKey` と `contentSha256` をDrive上の既存documentと照合する。
- **未取込**: つぐレジ＋が、永続 Changes cursor が無い場合にDrive全件baselineを再走査し、その直前に取得した `startPageToken` からChanges APIへ連続して、未処理documentを取り込む。既存documentは `duplicateImportKey` とリプレイ競合判定で二重取込しない。
- Drive上の売上をつぐレジ本体の業務DBへ逆輸入しない。売上取込の責任はつぐレジ＋側に限定する。

この分離により、復元した本体は欠落送信を回復し、つぐレジ＋はDriveに存在する未取込を回復する。一方のDBへ他方の業務データを逆流させない。

## 実装方針

- Drive の売上データを REGISTER / つぐレジの業務DBへ逆輸入しない。
- 復元DB内の `sales_journal` を正として、対応する `sync_outbox` が欠落しているイベントだけを `PENDING` で再構築する。
- 既存 `sync_outbox` 行、`SENT` 状態、Drive API の `SUCCEEDED` ACK、`drive_api_uploads.file_id`（documentId）は変更・削除しない。
- 再構築後に不足件数が 0 であること、既存SENT/ACK/documentId件数が変化していないことを検証し、成立しない場合は復元処理を失敗させて既存ロールバック境界へ戻す。
- 予備端末移行では terminalId 切替より前に再構築する。再構築outboxには復元元の `storeId / terminalId / generation` を保存し、旧イベントの duplicateImportKey を維持する。
- 通常生成される outbox にも source identity snapshot を保存する。JSON再生成時は現在のruntime identityではなくoutboxのsource identityを優先する。
- 復元成功後は Direct Drive upload worker を即時enqueueする。workerは PENDING をstagingしたうえで既存の `duplicateKey` と `contentSha256` を照合し、同一イベントを冪等処理する。
- つぐレジ＋は永続 `drive_changes_cursor` が無い場合、baseline開始前に `startPageToken` を捕捉して全件scanし、その後Changes APIへ移行する。baseline中の同時更新を取りこぼさない。
- つぐレジ＋の取込は `duplicateImportKey` と `SalesJournalReplayConflictPolicyV118`、SQLite `CONFLICT_IGNORE` を併用し、baseline/Changes再走査でも二重取込しない。

## 主な実装

- `RestoreSyncRebuildV136.kt`
  - `sales_journal LEFT JOIN sync_outbox` で欠落イベントのみ検出
  - 不足outboxの再構築
  - SENT / ACK / documentId 不変確認
  - Drive読込・売上逆輸入経路を持たない
- `BusinessSyncFoundation.kt`
  - `sync_outbox.source_store_id`
  - `sync_outbox.source_terminal_id`
  - `sync_outbox.source_generation`
  - outbox identity snapshot trigger
  - `OutboxPayloadAssembler` がsnapshot identityを使用
- `DataRestoreBootstrapV086.kt`
  - BKP-006再構築をBKP-005 terminal migrationより先に実行
  - 復元監査・結果へ再構築件数とSENT/ACK/documentId保持件数を記録
  - 復元成功後にDrive reconciliationをenqueue
- `GoogleDriveDirectUpload.kt`
  - Direct Drive処理開始時にPENDING outboxをstaging
  - 既存 `duplicateKey` / `contentSha256` / `file_id` 契約を継続利用
- `management-app/.../GoogleDriveDirectSync.kt`
  - cursorなし時のfull baseline
  - baseline開始前の `startPageToken` 捕捉
  - baseline後のDrive Changes API継続
  - Changes cursorをページ取込と同じSQLite transactionで永続化
- `management-app/.../SalesJournalImportRepository.kt`
  - `duplicateImportKey` / replay conflict判定による冪等取込

## 自動テスト

- 予備端末切替後も旧outbox identityを優先すること
- identity snapshotが不完全な場合は現在のpersisted identityへ安全にfallbackすること
- 再構築がterminal migrationより前に実行されること
- 不足outboxのみを対象にすること
- SENT / Drive ACK / documentId保持契約が存在すること
- DriveからREGISTERへ売上を逆輸入する実装を持たないこと
- 復元後にDirect Drive reconciliationへ接続されること

`V153Bkp006TwoSidedReconciliationContractTest` でSYN-004後の両方向契約を固定する。

- 本体: journal不足outbox再生成 → Direct Drive reconciliation
- 本体: `duplicateKey` + `contentSha256` によるDrive既存document照合
- つぐレジ＋: cursorなし → full baseline → captured startPageToken → Changes API
- つぐレジ＋: Changes cursorを取込transaction内で進めること
- つぐレジ＋: `duplicateImportKey` / replay policy / `CONFLICT_IGNORE` による二重取込防止
- 本体へDrive売上を逆輸入しないこと

## 実機未確認

以下はソフトウェア/CIだけでは完了扱いにしない。

- 実Driveに既に存在する売上JSONを含むバックアップからの復元後、duplicateKey照合で二重作成されないこと
- 実Drive未送信イベントを含む復元後、不足outbox再構築→送信→ACK/file_id保存まで完走すること
- つぐレジ＋の同期index/cursorを初期状態にした後、Drive既存documentが再走査され、既取込はduplicate、未取込だけが追加されること
- baseline走査中にDriveへ新規documentが追加されても、捕捉済みstartPageTokenからのChangesで取りこぼさないこと
- 予備端末移行で旧terminalId配下の既存Driveイベントと照合され、新terminalIdへ旧イベントを重複生成しないこと
- ネットワーク断・Drive認証切れ・再起動を跨いだreconciliation継続
- 大量ジャーナルを含む実データでの復元時間・再構築時間・再送挙動

これらは実機・実Google Drive環境で確認するまで `実機未確認` とする。
