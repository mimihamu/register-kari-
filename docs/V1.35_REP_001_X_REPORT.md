# v1.35 REP-001 X点検 / Z精算レポート

## 目的

v2.5の点検・精算要件に合わせ、X点検とZ精算で売上・税・値引・返品取消・支払・現金・件数・客数・点数を確認、印刷、PDF保存できるようにする。

## X点検の確定動作

- X点検は現在の営業セッションを集計してレポートを保存する。
- X点検では営業セッションを終了しない。
- X点検後も営業状態は `OPEN` のままで販売を継続できる。
- Z精算だけがREP-003の事前確認を通過した後に営業セッションを `CLOSED` にする。

## REP-001 集計内容

保存レポート/再印字用に `settlement_rep001_totals_v135` を追加し、レポート作成時点の次の値を固定する。

- 値引・割引合計: `sale_items.discount_amount`
- 消費税合計: `sales.tax_amount`
- 点数: `sale_items.quantity`
- 客数: `sales.guest_count`

既存の `settlement_reports` に保存済みの売上総額、返品取消、純売上、件数、支払方法別、開始釣銭、入金、出金、理論現金、実在高、過不足、未印刷、未会計伝票と合わせて表示する。

過去レポートの補完は `business_session_id` とレポートの `created_at` を上限に行い、現在の売上を過去X点検へ混入させない。

## 客数

v2.5の `sale_txn.guestCount` と保留伝票の客数要件に対応するため、既存 `sales` に互換列 `guest_count`、保留伝票用に `held_ticket_guest_count_v135` を追加した。

販売画面では担当者が客数を明示入力する。入力値は1〜999名。会計件数から客数を推測しない。

### 通常会計

入力された客数は次に確定される1件の `sales` INSERTでだけ消費され、同一SQL処理内のトリガーで `sales.guest_count` に保存した後、待機値を削除する。

### 保留・呼出

客数設定済みのカートを保留すると、`held_tickets` INSERTと同時に `held_ticket_guest_count_v135` へ客数を移し、作業中の待機値を消費する。

保留伝票を呼び戻すと、呼出・作業中カート退避・元伝票削除と同じSQLite transaction内でその客数を作業中カートへ復元する。作業中カートを退避してから別伝票を呼び出す場合も、元カートの客数は退避伝票へ保存され、呼出対象の客数に置き換わる。

伝票結合は両伝票の客数を合算する。999名を超える結合は拒否する。

伝票分割については人数を商品数量比で自動按分する仕様が存在しないため、客数を捏造しない。元伝票の客数を維持し、新しく作成する分割伝票は客数未設定とする。必要な人数は分割伝票呼出後に担当者が設定する。

取引中止時や空カートへ戻った場合は作業中の待機客数を破棄し、次取引への持ち越しを防ぐ。

既存売上や客数未入力の売上は0名のまま扱い、過去客数を会計件数から捏造しない。

## 画面表示

SCR-500-X / SCR-500-Zのプレビューに以下を表示する。

- 売上総額
- 値引・割引
- 消費税
- 返品・取消
- 純売上
- 売上件数
- 客数
- 点数
- 客単価（客数0の場合は `-`）
- 現金理論 / 現金実査 / 過不足
- 未会計保留伝票 / 販売途中明細 / 未完了決済 / 未印刷 / バックアップ状態

## 印刷

`OperationDocumentRenderer.renderSettlement()` でX/Z帳票を生成する。税・値引・客数・点数・客単価を含み、Xは末尾に「営業日は継続中です」、Zは「営業日を精算しました」と表示する。

## PDF保存

`SettlementPdfExportV135` を追加した。

- Storage Access Framework `CreateDocument(application/pdf)` で保存先を選択する。
- 保存済みのレポートNo.を `OperationsStore.previewSettlement(reportId)` で再構成し、その固定スナップショットをPDF化する。
- ファイル名は `TSUGUREGI_X_YYYYMMDD_No<reportId>.pdf` または `TSUGUREGI_Z_YYYYMMDD_No<reportId>.pdf`。
- SCR-500下部の「最新の保存履歴をPDF保存」から保存する。

## REP-003監査イベント

バックアップ失敗を責任者確認してZ精算を継続した場合、永続化される監査イベント名はv2.5準拠の次の値とする。

`Z_SETTLEMENT_BACKUP_FAILURE_ACK`

旧呼出し文字列 `Z_SETTLEMENT_BACKUP_FAILURE_ACKNOWLEDGED` はDB互換トリガーで上記名称へ正規化してから保存する。既存の追記専用監査履歴は書き換えない。

## テスト

`V135SettlementReportingTest` で次を確認する。

- REP-003バックアップ失敗ACKの正規イベント名
- ゼロ集計で客数を捏造しないこと
- 客数1〜999名の境界
- PDFファイル名とページ行数ポリシー

CIでは累積ソースゲート、ユニットテスト、Kotlin compile、POS/Plus/CD APKビルド、APK release identity/integrityを実行する。

## 実機確認が必要な項目

CI成功だけでは以下を確認済みとしない。

1. 販売画面で客数を入力し、会計確定後のX点検で客数・点数・客単価が正しいこと。
2. 客数未入力時に会計件数から客数が自動生成されないこと。
3. 客数を設定して保留→呼出→会計し、同じ客数がX点検へ集計されること。
4. 作業中カートを退避して別伝票を呼び出したとき、双方の客数が混線しないこと。
5. 取引中止後に客数が次取引へ残らないこと。
6. X点検実行後も販売を継続でき、営業セッションがOPENのままであること。
7. X/Zの画面、58mm/80mm印刷で税・値引・客数・点数が読みやすく表示されること。
8. PDFを端末ストレージへ保存し、日本語文字が欠けず、保存済みレポートと数値が一致すること。
9. Z精算のバックアップ失敗ACKで監査ログに `Z_SETTLEMENT_BACKUP_FAILURE_ACK` が保存されること。
10. 旧DBからの起動時に `guest_count`、保留伝票客数テーブル、REP-001スナップショット列/トリガーの互換追加が成功すること。

## 残る仕様差分

v2.5の伝票一覧は客数列を表示する。現在は客数の保存・保留・呼出・結合までは実装済みだが、既存 `HeldTicket` 一覧モデル自体には客数列がまだ無いため、一覧表示は別途同期が必要。
