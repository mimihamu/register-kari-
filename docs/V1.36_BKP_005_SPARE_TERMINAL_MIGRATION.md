# v1.36 BKP-005 予備端末移行／端末ID切替・採番安全性

## 正式仕様との対応

正式仕様 v2.5 の BKP-005 を、通常の同一端末復旧と明示的な予備端末移行に分離して実装する。

- 通常復旧では `storeId` / `terminalId` 不一致を従来どおり BLOCK する。
- 予備端末移行は明示的に `SPARE_TERMINAL` を選んだ場合だけ許可する。
- 予備端末は店舗未設定・売上履歴なし・terminal generation=1 の新品相当端末に限定する。
- バックアップ元店舗の確認には、暗号化 content bundle 内 `tax_invoice_settings/store_name` を使用する。
- content bundle を持たない旧 DB-only バックアップは、予備端末移行では fail-closed とする。
- 予備端末では旧 `terminalId` を再利用せず、新 `terminalId` を発行して固定する。
- `storeId` はバックアップ元を引き継ぎ、terminal generation は既知最大世代より増加させる。
- 店舗名の再入力、責任者 PIN 再認証、旧端末停止確認、Drive ACK/既存イベントの最大売上番号確認を要求する。

## 採番 floor

`SaleSequenceSafetyV136` は次の既知最大値を統合し、最大値を売上採番 floor とする。

1. `sales.id` の最大値
2. `sales_journal` の `SALE` イベント `aggregate_id` 最大値
3. `sync_outbox.status='SENT'` に対応する送信済み SALE journal 最大値
4. `sqlite_sequence` の `sales` 値
5. `sync_runtime_settings/bkp005_sales_sequence_floor` の永続 floor
6. 復元前端末で得られた既知最大値
7. 復元バックアップ DB で得られた既知最大値
8. 予備端末移行時に Drive ACK / 既存イベント側で確認した最大番号

floor は単調増加で保存し、`sqlite_sequence` を floor 以上へ引き上げる。新規販売前にも `SaleSequenceSafetyV136.enforceBeforeSale()` を実行し、次の AUTOINCREMENT ID が既知 floor 以下へ巻き戻らないようにする。

予備端末移行時に外部最大番号を確認できない場合、または入力値・端末状態に矛盾がある場合は販売継続可能な移行計画を作らず fail-closed とする。

## 復元処理とロールバック

`DataProtectionManager.stageRestore()` で復元計画を作り、次回起動時に `PendingRestoreApplierV086` が適用する。

復元適用は次の rollback 境界内で行う。

1. WAL-safe な復元前 DB snapshot 作成
2. 候補 DB 配置と integrity / foreign-key 検証
3. schema migration と最終 schema 検証
4. BKP-005 の store/terminal identity、generation、採番 floor 適用
5. `operation_audit` へ復元適用記録
6. BKP-003 content bundle 適用
7. journal outbox の stale PROCESSING / STAGED を再送可能状態へ復旧
8. 最終 DB 検証

途中で例外が発生した場合は content 設定と DB の双方を復元前状態へ戻す。

## 監査証跡

復元予約および復元成功の監査には少なくとも次を残す。

- 復元モード

- `storeId`

- 新 `terminalId`
- source generation
- target generation
- sale sequence floor
- Drive ACK / 既存イベントで確認した最大番号
- 実行責任者 (`operator_name` / `actor_name`)
