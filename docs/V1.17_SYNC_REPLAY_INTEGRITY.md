# v1.17 同期リプレイ整合性

## 目的

正常な再送は従来どおり冪等に扱い、同じ論理識別子で業務内容だけが異なる入力は成功扱いしない。

## つぐレジ

`sales_journal.event_id` を不変識別子として扱う。同じeventIdの再投入で businessDate、eventType、aggregateId、payload、createdAt が既存値と異なる場合はDB境界で拒否する。完全一致の再投入は従来の重複処理に渡す。

`sync_outbox.object_key` は送信前の保存先変更で変化し得るため不変比較には含めない。outboxでは同じeventIdに対するdestinationの食い違いを拒否する。

ガードはUI表示前にContentProviderから設置する。

## つぐレジ＋

`imported_journal.duplicate_import_key` は論理重複キーとして使われている。v1.17では同じキーに対し、schemaVersion、readerVersion、duplicateKeyVersion、eventId、eventType、storeId、terminalId、businessDate、aggregateId、occurredAt、payloadSchema、payload、totalAmountのいずれかが異なる入力をDB境界で拒否する。

sourceName、sourceUri、rawJson、importedAt、importRunIdは輸送・監査メタデータであり、同じ論理文書の再送でも変化し得るため比較対象にしない。

ManagementDatabaseはversion 5へ更新し、既存DBのアップグレード時にもガードを設置する。

## 検証

v1.17専用unit testに加え、累積unit test、3アプリのKotlin compile、3 APK build、APK identity・SDK・launcher・ZIP・署名検査、Artifact取得後のSHA-256独立再計算を行う。

実機での同期および既存DBの実端末移行は最終総合実機試験へ繰越す。

## v1.18 追補: 同期衝突の隔離・監査

v1.17のDB guardが検出する同一 `duplicate_import_key`・異内容を、通常import経路ではDB例外になる前に `NEW / IDENTICAL / CONFLICT` へ分類する。

- NEW: 通常挿入。
- IDENTICAL: 従来どおりduplicateとして冪等処理。
- CONFLICT: `DUPLICATE_KEY_MISMATCH` のrejectionとして同じimport runへ記録し、batch全体は継続する。

CONFLICTは `rejectedCount` に含め、runを `COMPLETED_WITH_ERRORS` として完了させる。これにより決定的衝突を一時障害として再試行し続けず、Google Drive同期は論理import完了後の既存fingerprint記録へ進める。Drive上の文書が変更されればmodifiedTime/content hashの変化により再評価される。

比較対象はv1.17 guardと同じ不変業務項目とし、sourceName / sourceUri / rawJson / importedAt / importRunId は輸送・監査メタデータとして比較から除外する。v1.17のDB guard自体は最終防御層として残す。

v1.18の正式検証も累積unit test、3アプリKotlin compile、3 APK build、APK identity・SDK・launcher・ZIP・v2署名、Artifact、SHA-256独立再計算まで行う。実機Drive同期と実端末DB確認は最終総合実機試験へ繰越す。
