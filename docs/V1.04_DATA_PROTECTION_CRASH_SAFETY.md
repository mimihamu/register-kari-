# v1.04 データ保護・クラッシュ安全性強化

## 目的

初期リリース前のデータ保護再点検で、正式バックアップと復元ファイル置換に残っていたクラッシュ時の危険箇所を安全側へ修正する。

対象はバックアップ/復元のファイルI/Oだけであり、売上・税・値引・支払・印刷・Google Drive・顧客表示の業務ロジックは変更しない。

## 1. `VACUUM INTO` 失敗時のWAL-safe fallback

通常のバックアップDB作成は従来通り `VACUUM INTO` を優先する。

従来のfallbackは `PRAGMA wal_checkpoint(FULL)` の結果を確認せず、続けて `register.db` 本体をコピーしていた。WALに未checkpoint frameが残っている場合、本体ファイルだけをコピーすると直近commitを含まないsnapshotになる可能性がある。

v1.04ではfallback時だけ次の条件を必須にする。

1. `PRAGMA wal_checkpoint(TRUNCATE)` を実行する。
2. `busy == 0` かつ `logFrames == checkpointedFrames` の場合だけ次へ進む。
3. `SQLiteDatabase.beginTransaction()` でEXCLUSIVE transactionを取得する。
4. transaction取得後に `register.db-wal` が不存在または0 byteであることを再確認する。
5. ここまで成立した場合だけ `register.db` 本体をstagingへコピーする。
6. checkpointとlock取得の間に別writerがcommitしてWALが再生成された場合は、その試行ではコピーしない。
7. 最大3回で安全条件を満たせなければバックアップ作成そのものを失敗させる。

重要なのは、バックアップ作成に失敗しても現在の売上DBを変更・削除しないことである。安全性を確認できないsnapshotを「成功」として残すより、バックアップを失敗させる。

## 2. crash-safe atomic replacement

従来の `DataProtectionManager.atomicReplace()` は、targetが存在する場合にtargetを先にdeleteしてからrename/copyしていた。この方式では、delete直後にプロセスが終了すると、例外処理やロールバック処理自体が実行されない時間窓がある。

v1.04では `CrashSafeFileReplaceV104` を追加し、次の方式へ変更する。

- 既存targetを先に削除しない。
- sourceが別directoryの場合は、まずtargetと同じdirectory内の一時ファイルへcopyし `FileDescriptor.sync()` する。
- sourceまたはstagingを `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)` で確定する。
- atomic moveを提供できないfilesystemでは、安全性を落とすcopy/delete fallbackを行わず失敗させる。
- `ATOMIC_MOVE` で既存targetを置換できるかはFileSystemProvider依存であり、置換できない実装では既存targetを先に消さず、そのまま失敗させる。
- move失敗時は既存targetを保持する。
- move成功後の別directory側source削除はcleanupとしてbest-effortにし、targetが既に確定した後の掃除失敗を「置換失敗」へ戻さない。
- sibling stagingの掃除は1時間以上経過した一時ファイルだけを対象にし、並行処理中のstagingを消さない。

この共通処理を使う既存経路は、バックアップarchive確定、バックアップimport、復元予約DB、restore plan、v0.86 rollback snapshot、起動時のDB置換、バックアップmetadata等である。

## 3. 保持する既存安全策

以下は変更しない。

- バックアップ前のデータ整合性診断
- バックアップDBの `PRAGMA integrity_check`
- 外部キー検査
- 必須table検査
- SHA-256 manifest検証
- 復元予約時の責任者PIN
- 営業中/未会計cart/保留伝票/未完了印刷/未送信Drive outboxがある場合の復元禁止
- v0.86の復元前WAL-safe rollback snapshot
- 復元失敗時のrollback
- 既存バックアップのretention policy
- Sales SQLite / Sales Journal / Drive JSON / sync fingerprint / imported sales / SENT Outbox / quarantine / sync history / receipt reprint audit / backup DB / rollback DBの自動破壊禁止方針

## 4. テスト

`V104DataProtectionCrashSafetyTest` で次を固定する。

- checkpointのbusy/未完了をfallback許可しない
- WALがnon-zeroならraw DB copyを許可しない
- checkpoint → EXCLUSIVE transaction → WAL再確認 → copy の順序
- 同一directoryの既存targetをatomic replaceできる
- 別directory sourceはtarget directoryへstagingしてからatomic moveする
- `atomicReplace()` が既存targetをpre-deleteしない
- target確定後のsource cleanupを致命エラーへ戻さない
- POS版番号 `134 / 1.04.0-dev.1`
- 文書化と実機試験繰越

## 5. 実機確認

以下は最終総合実機試験へ繰越する。

- 実端末SQLite version差による `VACUUM INTO` 成否
- fallbackを意図的に発生させた状態でのバックアップ作成
- backup作成中の並行売上/DB write
- 実端末FileSystemProviderで既存targetへのatomic moveが成立すること
- backup/restore確定直前のprocess kill
- backup/restore確定直前の端末再起動
- 復元後のSQLite整合性、営業日、売上、支払、印刷queue、Drive outbox確認
- 長時間運用下での自動バックアップ

実機未確認事項を確認済みとは扱わない。
