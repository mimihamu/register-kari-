# v1.34 Drive page commit checkpoint recovery

## 目的

v1.33ではDrive direct statusのrun start / page progress / success / failureを`SharedPreferences.Editor.commit()`へ変更し、SharedPreferences mutation自体のdurabilityを強化した。

ただし、次のcross-store crash windowは残っていた。

1. SQLiteでpage import / fingerprint更新がcommitされる
2. `SharedPreferences`へpage progressを`commit()`する
3. 1と2の間でprocessが終了すると、SQLiteは1 page先行しているのにdirect status countersは前pageのまま残る

v1.34はこのwindowを「2ストアを1つのtransactionにする」方式ではなく、SQLite page transaction内へ復旧checkpointを同居させる方式で回復可能にする。

## 実装

### 1. page最外SQLite transaction

Drive 1 pageごとに`pageDb.beginTransaction()`を開始する。

既存の`SalesJournalImportRepository.importDocumentsWithCommitHook()`は内部でもtransactionを開始するが、Android `SQLiteDatabase`はnested transactionをサポートし、外側transaction終了時にnested transactionを含めてcommit / rollbackする。

そのためv1.34では、同じ最外page transactionへ以下を含める。

- journal import / rejection
- changed JSONのDrive fingerprint更新
- content SHA-256が同一だったファイルのremote-version fingerprint更新
- v1.34 page progress checkpoint

checkpoint書込みまで成功した場合だけ最外transactionをsuccessfulにする。

### 2. SQLite checkpoint

自己管理table：

`drive_sync_progress_checkpoint_v134`

singleton rowとして以下を保持する。

- `run_token`
- listed
- downloaded
- unchanged
- imported
- duplicates
- rejected
- errors
- committed_at

`ManagementDatabase`のDB versionは変更しない。v1.34専用storeが`CREATE TABLE IF NOT EXISTS`で管理する。

### 3. SharedPreferences progress publication

最外SQLite page transactionがcommitした後に、v1.33の

`GoogleDriveDirectSyncStatusDurabilityV133.progress()`

で同じcountersをSharedPreferencesへ同期`commit()`する。

通常時はここまで終わるため従来と同じdirect statusが表示される。

### 4. process kill時の復旧

SQLite page commit直後～SharedPreferences progress commit直前にprocessが終了した場合、次processではSQLite checkpointだけが1 page先の値を保持している。

v1.34では新しいContentProviderを最優先で起動する。

1. v1.34 page checkpoint recovery: `initOrder=400`
2. v1.31 orphaned-run recovery: `initOrder=300`
3. v1.30 verification-history recovery: `initOrder=200`
4. Drive bootstrap: `initOrder=100`

v1.34 providerはprocess-wide barrierを最初にresetし、checkpointを確認する。

- direct statusが`running=true`
- SharedPreferencesの`run_token`とcheckpointの`run_token`が一致

この両方を満たす場合だけ、checkpoint countersをv1.33 durable progress経路でSharedPreferencesへ再publishする。

その後checkpointを削除し、v1.31 orphan recoveryへ渡す。したがってv1.31が作成する中断履歴は最後にSQLite commit済みのpage countersを使用できる。

### 5. stale checkpoint

success / failure finalization済み、または別run tokenのcheckpointはdirect statusへ適用しない。

staleと判定したcheckpointは削除する。

## fail-closed

v1.34 startup checkpoint recoveryで以下が失敗した場合はv1.32 barrierをblockする。

- Management DB open
- checkpoint schema準備
- checkpoint read
- checkpoint countersのSharedPreferences durable republication
- checkpoint delete transaction

v1.31 orphan recovery providerはv1.34以降、自身ではbarrierをresetしない。v1.34 providerがblockしたprocessではorphan recovery / history recovery / Drive bootstrapへ進めない。

次processでv1.34 providerがbarrierをresetし、checkpoint recoveryから再試行する。

## 既存保証

以下を維持する。

- v1.21 single-flight / run-token ownership / immediate work coalescing
- v1.22 import + changed-file fingerprint atomicity
- v1.23 committed page progress / run counter reset
- v1.24 importer compatibility replay
- v1.25 failure progress ownership
- v1.26-v1.30 verification history consistency / ownership / recovery
- v1.31 orphaned-run recovery
- v1.32 startup recovery failure barrier
- v1.33 direct status synchronous durability

SharedPreferences schema、verification history schema、WorkManager unique work名・周期、ContentProvider 300/200/100の既存相対順は変更しない。

## v1.34で解消対象とする境界

`SQLite page commit -> SharedPreferences progress commit`

の間でprocessが終了した場合に、最後にSQLiteへcommit済みのpage countersを次processで復元できるようにする。

これはSQLiteとSharedPreferencesを1つの物理transactionに統合するものではない。SQLite内のcheckpointをrecovery source of truthとして使うことで、cross-store crash windowをrecoverableにする。

## 実機未確認

CI / JVM testでは確認済み扱いにしない。

- importありpageのSQLite outer/nested transactionをcommit直後にprocess kill
- content SHA同一fingerprint-only page commit直後にprocess kill
- document 0件page checkpoint commit直後にprocess kill
- SQLite commit後、SharedPreferences progress commit前の強制killでcheckpoint countersがorphan historyへ反映されること
- progress republication後、checkpoint delete前の再killがidempotentに復旧すること
- checkpoint delete後、v1.31 orphan finalization前の再kill
- stale checkpoint + 新run start直後killで別runへ誤適用しないこと
- checkpoint DB read/write/delete失敗時に400 providerがbarrierをblockし、300/200/100へ進まないこと
- 次processで400 -> 300 -> 200 -> 100順に再試行されること
- 実端末でnested transactionにより既存import性能・ANR特性が許容範囲であること

これらは最終総合実機試験へ繰り越す。
